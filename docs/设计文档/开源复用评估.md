## 0. 一句话结论

**通用办公组件（文档内核、表格网格、PDF、图片）开源生态很热闹，可以大量复用；但"中国工程验收资料管理"这个垂直场景，GitHub 上是个空白 —— 最高星的同类项目只有 52 星且无许可证，`construction quality acceptance` 关键词搜索结果为 0。**

所以：**骨架和器官可以借，行业脑子和业务逻辑必须自己长。** 而且这一轮还挖到一个意外收获：**dsh 官方生态里已经有人做了 Office 插件，它直接验证了我们 A+ 路线的可行性，还顺手把我们的组合包写法纠正了两处。**

## 2. 同领域开源现状：一片空白（这是好消息也是坏消息）

### 2.1 检索结果

| 检索词 | 结果总数 | 最高星 | 判定 |
|---|---|---|---|
| `construction quality acceptance` | **0** | — | **完全空白** |
| `construction document management` | 120 | 52（`xinsuifan-web/Cloud-Platform-for-Construction-Project-Bidding`，**无许可证**，投标 SaaS） | 不适用 |
| `engineering document management system` | 136 | 9（`Talengi/phase`，EDMS，**NOASSERTION**，2022 年后停更） | 太早期 |
| `工程资料`（中文） | 1073，但前排全是 NLP 语料/书籍列表 | 无关 | 中文检索在 GitHub 上质量极差 |

### 2.2 结论

**没有可整机复用的开源项目。** 原因不是我们没找到，而是这个场景的三个特征决定了它长不出开源项目：

| 特征 | 后果 |
|---|---|
| **强地方性**：各省市验收资料清单、表格格式、编号规则不同 | 通用开源项目做不了，一做就要维护 N 套省标 |
| **强交付性**：用户要的是"能过甲方验收"，不是"功能好玩" | 开源社区缺乏动力（贡献者自己用不上） |
| **已被商业软件占据**：筑业、品茗等做了二十多年 | 商业软件的存在压低了开源的可能性 |

**对我们的意义：**
- ✅ **"自建"这个决定是对的，不是重复造轮子 —— 是根本没人造过这个轮子。** 我们的护城河在**模板资产（37 份 + 171 占位符）+ 清单（8 分册 56 项）+ 规则（填数规则.yaml）**，这三样是可积累的垂直资产，不是代码
- ⚠️ 反过来说：**没有任何现成架构可以抄**，§2.1 的分层和 §3 的模块划分必须靠自己想清楚（v2.0 已经做了）

### 3.2 关键判断

**① 许可地图极其清晰：编辑内核里 Apache-2.0 的只有两家 —— genoffice 和 Univer。**

AGPL-3.0 意味着：只要分发给别人（哪怕只是给同行用），整个软件都要开源，或者买商业授权。**我们现在是自己用，但"将来可能给同行"这个可能性必须留住**（v1.0 §5.2 已有此判断）。所以 AGPL 那一批（ONLYOFFICE / SuperDoc / ranuts）**只能当参考，不进架构**。

**② genoffice 的 `packages/docx-engine` 实测依赖只有 4 个：**

```json
{ "name": "@genoffice/docx-engine", "version": "0.1.0", "license": "Apache-2.0",
  "dependencies": {
    "@genoffice/pptx-engine": "*",
    "fast-xml-parser": "^5.3.4",
    "jszip": "^3.10.1",
    "utif2": "^4.1.0"
  } }
```

**没有 electron、没有 React、没有 AI 依赖、没有原生模块** → **可以干净地嵌进我们自己的壳**（无论 Electron 还是 Tauri）。这条实测直接消灭了我上一轮"纯 TS 无 Electron 依赖"推断中的不确定性。

它的仓库结构也印证了架构设计：`packages/` 下 `docx-engine` 与 `electron-utils` **并列**，`apps/` 下 7 个应用共用（docs / html / markdown / pdf / sheets / shell / slides）。**这正是"一个引擎、多个应用"的形态，跟我们 §2.1 的分层同构。**

**③ Univer 的保真度存疑，这是它和 genoffice 的根本分野。**

Univer 的定位是"full-stack framework for creating and editing spreadsheets / word processor / presentation"，**它的数据模型是自己的（`.univer` 文件）**，导入 `.docx` 是**转换**，导出也是**重新生成**。

而我们要处理的 37 份模板是**含合并单元格、页眉页脚、下划线填空位、精确列宽**的既有 docx。转换进出 = 大概率丢格式。**这跟红线 5（格式 100% 保留）直接冲突。**

→ 所以：**Univer 不适合承担"模板保真编辑"，但它适合做"表格网格编辑"（E3）和"从零生成"场景。**

### 3.3 ADR-6 结论（修订版）

| 路线 | 用途 | 结论 |
|---|---|---|
| **genoffice `@genoffice/docx-engine`** | **模板保真编辑 + 渲染 + 打印取页数据**（E0–E4 主线） | ✅ **主选** |
| Univer | ① E3 表格网格编辑的**参考实现**；② 从零生成场景（新建空白文档） | 🔶 备选，不承担保真 |
| docx.js / mammoth | 只能读渲染，不能编辑 | ❌ 不用于编辑 |
| SuperDoc / ONLYOFFICE / ranuts | AGPL 传染 | ❌ 不引入 |
| 保底 | 停在 E1 表单式 + Word 手改 | 🔶 退路 |

## 4. 意外收获：dsh 生态里已经有 Office 插件了

### 4.1 实测数据

```
dream-num/dsh-univer-office
  ★346  forks 33  open_issues 4  Apache-2.0  TypeScript  size 66645KB
  created: 2026-08-15   pushed: 2026-09-15（一天前）
  topics: deepseek-harness, deepseek-harness-plugin, dsh, dsh-plugin, office, office-harness
  homepage: https://office.univer.ai
  npm: dsh-univer-office@0.2.14
```

**这是 Univer 团队（dream-num）为 DeepSeek Harness 做的官方级 Office 插件。**

### 4.2 它做了什么

| 能力 | 内容 |
|---|---|
| Doc | 段落、富文本、列表、任务、**表格、图片、图表、页眉、页脚、分页** |
| 导入导出 | **`.docx` 导入 / 导出**（Sheet 支持 xlsx/csv/tsv，Slide 支持 pptx） |
| 校验与审查 | 文档回读、**页面截图**、**PDF 打印**、实时预览 |
| 工作流 | **隔离草稿（isolated draft）+ 语义对比 + 批准/丢弃**；"Approval and discarding always require an explicit user request" |
| 工具 | 14 个：`univer_new` / `_status` / `_worktree` / `_unit` / `_import` / `_inspect` / `_execute` / `_export` / `_lint` / `_compile_svg` / `_screenshot` / `_print_pdf` / `_api` / `_resources` |
| 依赖 | `puppeteer-core`（截图/打印）、`libsql`（本地库）、`@univerjs-pro/cli-assets` |

### 4.3 它对我们的三个直接影响

**① 直接验证了 A+ 路线是官方支持的 —— 我们的 `dsh-yanshou-docs` 设计方向没错。**

它的 `package.json` 关键字段：

```json
"dsh": {
  "bundle": { "patch": "./cordis.patch.yml" },
  "client": { "platform": "web", "inject": ["@deepseek-ai/dsh-client-ui-chat", "..."] }
}
```

**`dsh.bundle.patch` 就是我们 v1.0 用的机制**，一个真实可用的第三方插件正在这么干。这比官方文档更有说服力。

**② 顺手纠正了我们组合包的两处写法（比 v1.0 的做法更规范）：**

| 项 | v1.0 我们的做法 | dsh-univer-office 的做法 | 采纳 |
|---|---|---|---|
| `@deepseek-ai/*` 依赖 | **完全不声明**（理由：子包依赖图不完整） | **用 `peerDependencies` 声明** + 版本范围 `^0.1.5-rc.1` | ✅ **改用 peerDependencies** —— 更规范，且能让宿主版本不匹配时响亮报错 |
| `dsh` 字段 | 只有 `bundle.patch` | `bundle.patch` + `client` 客户端注入 | 我们**只用 bundle，不用 client**（`client.platform = web` 会绑 dsh 的 web UI，违背我们"不走 dsh UI 通道"的原则） |

**③ 给我们一个"过渡方案"和一个"参考实现"：**

- **过渡方案**：P4 自建壳还没做出来之前，可以先用 `dsh web` + `dsh-univer-office` 顶一阵，验证业务逻辑（但注意它的 Doc 是 Univer 模型，**不能用来处理我们的 37 份模板**）
- **参考实现**：它的**隔离草稿 + 语义对比 + 批准/丢弃**机制，正是我们 §4.9「半自动同步」要的东西 —— **照它的交互模式设计**，不用从头想

### 4.4 但不要直接用它的三条理由

| # | 理由 |
|---|---|
| 1 | **它绑 dsh 的 web UI 体系**（`client.inject: dsh-client-ui-*`），用了就等于接受 dsh 的界面形态，违背 v1.0「只走 sdk 最小契约面、编辑区自建」的核心风险控制 |
| 2 | **它是通用 Office 能力，不是验收资料业务**：模板填充、编号池、目录树、打印状态、填数规则 —— 它一样没有，我们该写的还得写 |
| 3 | **依赖 `@univerjs-pro`**：Univer 有 Pro 商业版，需警惕误用 Pro 授权功能（这一条要真机核对它的 LICENSE/使用条款） |

## 5. 逐模块复用清单（14 个模块 · 借什么、自建什么）

图例：**借** = 直接引入开源件；**参** = 参考其思路/写法，自己实现；**建** = 必须自建（无可用件）

| 模块 | 结论 | 借什么 / 为什么 |
|---|---|---|
| **M01 工程底座** | **建** | 无可用件。`project.json` 结构是业务定制的。可借 *zod*（TS 侧 schema 校验）或 Python 侧 `jsonschema` 做校验 |
| **M02 清单与目录树** | **建 + 参** | 业务逻辑自建；树控件用壳自带的（Electron/Tauri 侧现成组件） |
| **M03 项目档案** | **借（表单库）** | 业务字段自建；表单渲染借成熟库（如 *react-hook-form* + schema 驱动），省 30% 工作量 |
| **M04 规则资产** | **建 + 参** | 资产体检脚本我们已有 12 个（`03_工具脚本/`）；YAML 解析借 *js-yaml* / PyYAML |
| **M05 填数引擎** | **建**（核心资产） | 无可用件。这是本项目最核心的独创部分。规则 DSL 可参考 *json-logic* / *CEL* 的极简子集思路，但**不引入**（避免过度设计） |
| **M06 文档生成** | **建** | 生成/编号/三选一出路是业务逻辑。模板拷贝 + 原子写盘自建 |
| **M07 子表与结构** | **建** | 无可用件。子表识别（按表头列名）是业务独有的。行克隆算法参考 v1.0 §4.4（已验证思路） |
| **M08 校验闸门** | **建** | 无可用件。口径（哪些算残留、哪些不算）是业务定的 |
| **M09 文档编辑** | **借（关键）** | **`@genoffice/docx-engine`（Apache-2.0，依赖极干净）**。这是本次复用清单里价值最高的一项，省下的工作量按**月**计 |
| **M10 打印** | **借 + 建** | 预览与页数据取 genoffice 渲染输出；已打印状态与过滤自建 |
| **M11 导出与组卷** | **借** | ① docx→PDF：优先复用 M09 内核的打印为 PDF；② **PDF 合并与加页码用 `pypdf`**（★10,204）；③ **不用 PyMuPDF**（★10,717 但 **AGPL-3.0**，商用要买授权） |
| **M12 附件与影像** | **借** | EXIF 纠正：JS 侧 *exifr*（MIT，★1,247）或 Python 侧 *Pillow*；压缩用 Pillow。都是成熟件 |
| **M13 AI 助手** | **借（底座）+ 建（业务）** | 底座用 dsh（已有）；**工具设计参考 `dsh-univer-office` 的 14 工具划分与"草稿-审批"模式**；起草/抽取/汇总的业务 prompt 自建 |
| **M14 回收站与留痕** | **建** | 业务逻辑自建；JSONL 追加写自建（几十行） |

### 5.1 明确"不引入"的清单与理由

| 不引入 | 理由 |
|---|---|
| **`python-docx` / `docxtpl`（★2,703, LGPL-2.1）** | 它们基于 python-docx 做"读取-重建"，**会重排部件、丢样式**，违反红线 5。我们的部件级替换已经跑通 171/171，**不需要引入** |
| **`poi-tl`（★5,149, Apache-2.0）** | Java 生态，与我们 Python 引擎不搭。**但它的"标签语法"设计值得一看**（我们的 `{{key}}` 更简单，不需要改） |
| **`docxtemplater`（★3,627）** | **NOASSERTION = 商业双许可**，商用要付费 |
| **PyMuPDF（★10,717）** | **AGPL-3.0** |
| **SuperDoc / ONLYOFFICE / ranuts/document** | **AGPL-3.0** |
| **ONLYOFFICE Document Server** | AGPL + 需跑服务端，对单机桌面产品太重 |
| **LibreOffice WASM** | 50MB 载荷 + 约 800MB 内存 + 需 Spectre 头 |
| **dsh-univer-office（作为直接依赖）** | 绑 dsh web UI + 通用能力非业务能力（详见 §4.4） |
| **任何需要 `allowBuilds` 授权的 npm 包** | 供应链红线（v1.0 红线 8） |

## 7. 验证清单（P4 之前必做，约 1 天）

这四项按顺序做，**任一项大面积不通过就退路**（退路见 §3.3）：

| # | 验证项 | 方法 | 通过标准 |
|---|---|---|---|
| V1 | **依赖可引入** | 在我们壳里 import `@genoffice/docx-engine`，跑通 `pnpm install && typecheck` | 无原生模块编译、无 Electron 强依赖 |
| V2 | **37 份模板渲染** | 逐份打开截图比对 | 排版不崩、表格不错位、页眉页脚在 |
| V3 | **保真写回**（**最硬的一关**） | 每份改一个字 → 保存 → 跑 `03_工具脚本/diff_parts.py` | **只有被改的部件变了，媒体文件逐字节一致** |
| V4 | **打印取页数据** | 打印预览 / 导出 PDF，取页码 | 页码正确，支撑"已打印"标记与整册目录页 |

**V3 是我们和 genoffice 之间唯一的真问题** —— 它的"字节保留往返"理论上就该过这关，但**必须实测**，不能信宣传。

## 8. 复用的净收益（老实账）

| 项 | 省下的 | 说明 |
|---|---|---|
| docx 编辑内核（E0–E4 渲染 + 编辑 + 保真写回） | **大头，按月计** | 这是原方案里最贵的自研项，靠 genoffice 基本免掉 |
| PDF 合并 / 加页码 | 数天 | `pypdf` 几十行搞定 |
| 图片 EXIF / 压缩 | 1–2 天 | `exifr` / Pillow |
| 表单渲染（M03） | 3–5 天 | 成熟表单库 |
| 交互模式（半自动同步） | 2–3 天 | 照 dsh-univer-office 抄 |
| **合计** | **≈ 一个半月到两个月的工作量** | 粗估，按"一个人干"的口径 |
