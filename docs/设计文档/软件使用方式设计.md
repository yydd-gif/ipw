## 0. 一句话

**建一个工程 = 建一个文件夹；点一次「一键成册」= 套完 37 份模板并填好字段；打完印标记状态；最后整册导出 PDF 归档。** 39 个项目字段全程只填一次。

## 1. 软件形态与数据落盘

### 1.1 形态
- Windows 桌面客户端（Tauri 外壳 + 内嵌编辑内核），双击图标即开
- 首屏 = **工程管理器**：新建工程 / 打开工程 / 最近打开 / 从文件夹导入
- 单机可用，不依赖数据库、不依赖网络；联网时解锁 AI 能力
- **基础功能离线可用，AI 功能需联网授权**（决策 12）

### 1.2 一个项目 = 一个工程文件夹（决策 7）

```
YY123-岳阳市XX局信息化项目/
├─ project.json                 项目信息(39字段) + 编号池 + 打印状态 + 目录树快照
├─ 一、依据分册/
├─ 二、过程分册/
│   └─ 1、开工报审表/
│       ├─ YY123-KGBSB-01_开工报审表.docx
│       └─ YY123-KGBSB-02_开工报审表.docx
├─ 三、图纸分册/
├─ 四、变更分册/
├─ 五、初步验收与试运行分册/
├─ 六、竣工验收报告/
├─ 七、竣工验收分册/
├─ 八、封面页/
├─ _附件/                       上传的 PDF / 照片 / 扫描件
├─ _导出/                       生成的 PDF / 图片
└─ _回收站/                     删除的目录项（可还原）
```

**为什么这么设计：** 整个文件夹拷走就是一套完整资料，U 盘、共享盘、微信传都行。资料员那边不需要装软件也能看。代价是多人同时编辑要靠共享盘文件锁，单机作业无压力。

## 2. 四个使用阶段

### ① 建档（一次性，约 5 分钟）

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | 新建工程 | 选一个空文件夹，起个工程名 |
| 2 | 填项目信息 | 强制只要 **4 类**：项目名称、合同编号（如有）、建设/施工/监理三方单位；其余 35 项可后补 |
| 3 | 加载目录 | 自动读 `软件目录.docx` → **8 分册 56 项**建树，不硬编码 |
| 4 | 一键成册（可选） | 可当场把 37 份套模板文档全生成，也可以后面慢慢来 |

### ② 填报（贯穿整个施工期）

**两种入口，按心情用：**

- **一键成册（批量）**：右键工程根 →「生成全部」→ 引擎遍历 56 项
  - 有模板的 37 项：套模板 → 填 39 字段 → 分配编号
  - 无模板的 18 项：建空白 docx / 留上传位
  - **手动触发，不自动跑**（决策 3）
- **单份处理（精细）**：左树点某项 → 右侧打开 → 项目级字段已自动填好（浅灰显示），待填字段高亮 → 补完 `Ctrl+S`

**字段分两层：**

| 层 | 范围 | 行为 |
|---|---|---|
| 项目级（39 字段） | 全册 | 录一次，全局带入；改一处，全册同步 |
| 文档级 | 单份 | 如「移交地点」，只在那一份里 |

**日期策略**：全部手填，软件不给默认值（按既定口径，12 个日期字段已停用）。
**未填字段呈现**：编辑区里**浅灰占位**显示，便于打印前肉眼扫（决策 9）。

### ③ 打印（送审前）

- **打印预览**：整册 / 分册 / 单份 三档
- 打印后自动标记「已打印」，树节点 + 列表双处可见
- **打印状态最小粒度 = 单份**（决策 5）；分册/整册显示汇总进度（如 8/13）
- 支持「只看未打印」过滤，杜绝漏打、重复打

### ④ 交档（竣工归档）

- **导出粒度**：单份 / 按分册 / 整册
- **默认格式 PDF**（合并 + 统一编页码，决策 10）；另支持图片 PNG·JPG / 文档 docx
- **整册导出自动加目录页 + 页码**（决策 11）
- **导出文件名**：`{文档编号}_{表名}.pdf`，例 `YY123-KGBSB-01_开工报审表.pdf`

## 3. 界面三区（对标 `参考图.png`）

| 区域 | 职责 |
|---|---|
| **顶部功能区 Ribbon** | 工程级动作：新建 / 打开 / 一键成册 / 打印 / 导出 / 回收站 / AI |
| **左侧目录树** | 三页签：**表格目录 · 回收站 · 查找结果**；节点带状态色点 |
| **右侧编辑区** | Office 式编辑：格式工具条 + 行列标网格 + 表格编辑 + 插入图片 |
| **底部状态栏**（新增） | 当前文档 · 文档编号 · 已填字段数 · 打印状态 · 保存状态 |

**左侧树节点状态色点：**

| 颜色 | 含义 |
|---|---|
| 灰 | 待填（未生成或未填完） |
| 绿 | 已填完整 |
| 蓝 | 已打印 |
| 红 | 缺模板 / 缺必填项 |

**编辑内核形态（决策 2）**：**流式为主，进入表格单元格切换为网格编辑**。原因：模板本身是 docx 流式文件，纯 Excel 网格套不上；但表格类资料（开箱记录、调试记录、清单）在网格里编辑效率高得多，所以做局部网格。

## 4. 关键交互细则

### 4.1 一个目录项出多份文档怎么挂 —— **方案 A · 四级树**（决策 1）

```
二、过程分册
  └ 1 开工报审表
      ├ YY123-KGBSB-01 · 已打印
      └ YY123-KGBSB-02 · 待填
```

理由：一眼看清总共出了几份、每份什么状态；右键菜单作用对象明确（删这一份 vs 删整个目录项）；跟「编号在目录项内独立续排」的规则天然一致。

### 4.2 文档编号（定稿，软件侧照做）

```
有合同编号：  {合同编号}-{表名缩写}-{流水号}      例：YY123-KGBSB-01
无合同编号：  {表名缩写}-{流水号}                 例：KGBSB-01
```

| 规则 | 内容 |
|---|---|
| 表名缩写 | 表名每个汉字拼音声母取大写，如 开工报审表 → `KGBSB`；软件自动生成，人工可覆盖 |
| 流水号位数 | 默认 2 位；施工日志 / 周报 / 月报 / 试运行记录用 3 位 |
| 续排范围 | **单个目录项内独立续排**，每个目录项各自从 01 起 |
| 适用 | 只有模板内带「文档编号」标签的 **9 项**才编号 |
| 分配时机 | **生成文档那一刻**，取最小可用号，永久绑定（决策 4） |
| 删除 | 编号释放回**该目录项**号池 |
| 恢复 | 从回收站恢复时**取回原编号**，不重新分配 |
| 重排 | 同目录内删除后**不重排**（删掉 02，03 仍是 03） |

> 不重排的原因：已打印的纸质件编号必须与电子件永远一致。实时重排的话，中途删一份会让后号整体前移，发出去的纸质件当场对不上。
> **唯一主键用文档 ID**，编号只作展示与打印，不做索引（同表 01 号会重复）。

### 4.3 删除与恢复（决策 6）

- 可删的对象：**整个目录项** 或 **其中某一份文档**，两者都进回收站
- 回收站页签：列表 + 还原 + 彻底删除；还原后目录树位置不变
- 目录项删除后，其下文档一并进回收站，整体还原

### 4.4 模板缺失场景（18 项）

每个无模板项给三个出路：
1. **新建空白 docx** —— 软件给一个带项目信息页眉的空文档
2. **上传现成文件** —— 支持 docx / PDF / 图片，落在该目录项文件夹里
3. **标记跳过** —— 树节点标「缺」，导出时可选排除

### 4.5 附件与照片（决策 8）

- **优先挂在所属目录项文件夹**里（如 `六、竣工验收报告/9、文档移交表/附件/`）
- 不属于任何目录项的散件落工程根 `_附件/`
- 拖拽上传；图片自动 EXIF 方向纠正 + 压缩

## 5. AI 能力用在哪儿

| 场景 | 能力 |
|---|---|
| 施工日志 → 周报 | 按周聚合日志：`todayWork` 汇总、`weather` 统计、`workerCount` 取均值/峰值 |
| 周报 → 月报 | 二次聚合，沿用同一套口径 |
| 正文段落 | 项目背景 / 建设目标 / 建设内容 自动起草、润色、扩写 |
| 智能填表 | 粘一段文字或一份旧资料，自动抽字段回填 |
| 查错 | 必填项空缺、编号断号、日期逻辑错、单位名前后不一致 |

> 自动汇总链路的前置条件已备齐：施工日志正文 6 个字段（`weather`/`todayWork`/`workerCount`/`siteIssue`/`coordination`/`buildSite`）已全部占位。

**工程实现约定**

- 引擎用 Python 写在 `.workbuddy/engine/`（**不移植**，见下方 AI 层说明）
- docx 一律走**部件级操作**（zip 读入 → 逐 part 改 XML → 写回），不用 python-docx 重排，保证格式 100% 保留
- 缺值不填空、**保留 `{{key}}` 原样**，交给残留校验拦截 —— 宁可导出报错，不可导出半成品
- 引擎只读 `模版/`，输出到工程目录，**永不回写原始模板**

### 7.1 AI 层接入方式（决策 13，2026-09-12 工头拍板「A+ 不错」）

**dsh 以「官方 profile + 外部组合包」形式接入，不改 upstream 一行源码。** 详见 `规范/A+装配式集成方案.md`。

```
自建桌面壳（Ribbon / 三页签树 / 编辑区 / 打印 / 导出）      ← 自建，命根子
        │ 本地 IPC
        ▼
dsh --profile sdk（headless 后端，upstream 一行未改）
  ├─ dsh-base：模型适配 · 工具注册表 · 沙箱审批 · 会话日志   ← 官方提供
  └─ dsh-yanshou-docs（我们的组合包，树外，tarball 分发）    ← 只做接线
       └─ spawn → Python 引擎（.workbuddy/engine/*.py）      ← 真正干活
```

**三条硬约定**：
1. **插件层薄如纸** —— 只做「校验参数 → spawn 子进程 → 回 stdout」，文档处理逻辑全留在已验证的 Python 引擎里，**零重写**
2. **编辑区不走 dsh 的 UI 通道** —— 只走 `--profile sdk` 的 JSON-RPC，契约面最小，把 dsh 的破坏性变更挡在编辑内核之外
3. **模板保护变硬机制** —— `assertWritable()` 闸门 + 将来接 `ctx.sandbox` / `tools/pre-execute`，把「AI 绝不写 `模版/`」从口头规矩落成代码

**为何不 fork**：编辑内核 / 打印状态 / 一键成册批处理，fork 之后照样得自建，fork 只换来「永久接管一个 183MB / 55 包的框架」。抽身成本必须保持≈0。
