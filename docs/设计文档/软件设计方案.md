## 1. 产品定义

### 1.1 定位与对标

**一句话**：建一个工程 = 建一个文件夹；点一次「一键成册」= 套完 37 份模板并填好字段；打完印标记状态；最后整册导出 PDF 归档。**39 个项目字段全程只填一次。**

| 维度 | 内容 |
|---|---|
| 形态 | Windows 桌面客户端，双击图标即开 |
| 对标 | 「筑业云资料」——顶部 Ribbon + 左侧目录树 + 右侧 Office 式编辑区 |
| 差异化 | ① 模板驱动、清单可配；② 内建 AI（起草/润色/汇总/抽字段）；③ 数据落盘为普通文件夹，可拷可传可离线 |
| 核心价值 | 把「资料员手工套模板填表」这件每周重复的苦活，压缩成一次性录入 + 一键成册 |

### 1.2 用户与使用场景

| 角色 | 关心什么 | 软件要满足 |
|---|---|---|
| **资料员**（主用户） | 别填错、别漏打、别返工 | 字段只填一次、状态色点、只看未打印过滤、导出文件名规范 |
| **项目经理 / 工头** | 进度、合规、能不能过验收 | 一键成册、查错助手、整册导出、资料完整性一眼可见 |
| **施工员** | 少打字 | 施工日志 → 周报 → 月报自动汇总、正文自动起草 |

**使用节奏**：建档（一次性）→ 填报（贯穿施工期）→ 打印（送审前）→ 交档（竣工）→ 四个阶段的分工见《软件使用方式设计》第 2 节。

### 1.3 功能范围

**明确要做：**

| 域 | 功能 |
|---|---|
| 工程管理 | 新建 / 打开 / 最近打开 / 从文件夹导入；目录树自动加载（不硬编码） |
| 一键成册 | 按模板生成 37 份 + 18 项无模板项的三选一出路；填 39 字段；分配编号 |
| 编辑 | Office 式编辑：格式工具条、行列标、进表格切网格编辑、插图 |
| 打印 | 三档预览（整册/分册/单份）、调系统打印、已打印标记与持久化、只看未打印 |
| 导出 | PDF（合并 + 目录页 + 统一页码）/ 图片 PNG·JPG / docx；三档粒度 |
| 附件 | 上传、拖拽、EXIF 方向纠正、压缩 |
| 回收站 | 删整项 / 删单份 → 可还原（位置不变）→ 可彻底删除 |
| AI | 日志→周报→月报、正文起草润色、智能填表、查错助手 |
| 模板保护 | AI 与引擎一律不得写 `模版/` |
| 留痕 | 谁何时改了哪份哪字段，可回放 |

**明确不做（本期边界）：**

| 不做 | 原因 |
|---|---|
| 多人在线协同编辑同一份文档 | 单机 + 文件夹落盘；多人靠共享盘文件锁 |
| 云端存储 / 账号体系 | 数据主权在本地，客户资料不出内网 |
| 自定义分册/目录项结构 | 清单以 `软件目录.docx` 为准；结构调整走模板资产维护 |
| 自动填充日期 | 工头定：日期一律人工手写（`datePolicy.enabled = false`） |
| 模板内标注动态表格 | 工头定：子表由程序端按表头识别（`tablePolicy.mode = program-side`） |
| 让模型做确定性批处理 | 一键成册输入固定、输出唯一，交给 LLM 是几十次推理 + 不确定性 |
| fork dsh / 改 upstream 源码 | 升级成本与抽身成本必须 ≈ 0 |

### 1.4 领域概念模型

这是全软件的骨架，务必先看懂这张图再往下读。

```
工程（文件夹）
├─ 分册 × 8            （一、依据 …… 八、封面页）
│   └─ 目录项 × 55       （清单里的一条资料，如「1、开工报审表」）
│       ├─ 元数据：模板有无 / 资料类型 / 重要级别
│       ├─ 文档实例 × N   （该目录项下实际生成/上传的每一份）
│       │   ├─ docId       ← 程序唯一主键
│       │   ├─ docNo       ← 纸面编号（本项目内不唯一，只作展示与打印）
│       │   ├─ 填写状态 / 打印状态
│       │   └─ 文件路径
│       └─ 附件           （照片 / PDF / 扫描件）
└─ 字段 × 39            （项目级 39 个 + 文档级覆盖）
```

**三条容易搞错的关系，这里一次说清：**

1. **目录项 ≠ 文档**。一个目录项可以出多份文档（如开工报审表按标段出 2 份），所以树是四级的：分册 → 目录项 → 文档。
2. **docNo ≠ 主键**。文档编号在单个目录项内独立续排，不同目录项的 `01` 会重复 → **编号在项目内不唯一**，只能作展示与打印；程序内一切索引走 `docId`。这是**设计前提，不是缺陷**。
3. **字段分两层**。项目级字段录一次带入全册，改一处全册同步；文档级字段只在那一份里生效。文档级覆盖优先于项目级。

## 2. 总体架构

### 2.1 四层架构

```
┌────────────────────────────────────────────────────────────────────┐
│  L1 · 桌面壳（自建，命根子）                                        │
│  Ribbon 功能区 · 左侧三页签树 · 编辑区 · 状态栏                       │
│  打印预览与已打印标记 · 导出 PDF/图片/docx · 回收站                   │
│  编辑内核：docx 所见即所得 + 行列标 + 表格网格                        │
└──────────────────────────┬─────────────────────────────────────────┘
                           │ 本地 IPC（127.0.0.1 JSON-RPC 或 stdio）
                           ▼
┌────────────────────────────────────────────────────────────────────┐
│  L2 · AI 后端（dsh，upstream 一行未改）                              │
│  dsh --profile sdk                                                  │
│  ├─ @deepseek-ai/dsh-base                                           │
│  │    模型适配 · 工具注册表 · 沙箱与审批 · 会话日志 · 设置 · 凭据     │
│  └─ dsh-yanshou-docs（我们的组合包，树外，tarball 分发）              │
│        tools: yanshou_fill / _verify / _subtable / _numbering /      │
│               _aggregate                                            │
│        policy: 模板保护（拒绝写 模版/**）                            │
└──────────────────────────┬─────────────────────────────────────────┘
                           │ spawn（argv 传参，shell: false）
                           ▼
┌────────────────────────────────────────────────────────────────────┐
│  L3 · 引擎层（Python，确定性，真正干活）                             │
│  fill_engine · verify_engine · subtable_engine ·                    │
│  numbering_engine · aggregate_engine                                │
└──────────────────────────┬─────────────────────────────────────────┘
                           ▼
┌────────────────────────────────────────────────────────────────────┐
│  L4 · 数据层（普通文件夹，不依赖任何框架）                            │
│  project.json + 8 分册 docx + 附件 + 回收站                          │
└────────────────────────────────────────────────────────────────────┘
```

### 2.2 分层职责与边界

| 层 | 只做 | 绝不做 | 为什么这样切 |
|---|---|---|---|
| **L1 桌面壳** | 界面、交互、编辑、打印、导出、文件夹读写 | 不做文档内容计算 | 编辑内核与 AI 完全解耦，换 AI 底座不动壳 |
| **L2 AI 后端** | 模型调度、工具注册、审批、留痕 | 不做文档处理、不碰 UI | 「只走最小协议面」，把 dsh 的变更风险挡在编辑内核之外 |
| **L3 引擎** | 确定性数据变换（填充/校验/识别/编号/汇总） | 不联网、不调模型、不写模板 | 输入固定输出唯一 → 100% 可复现，可单测 |
| **L4 数据** | 存 | — | 普通文件，整包拷走即完整资料 |

**关键设计判断：L3 是「会干活的」，L2 只是「会喊话的」。** 插件层薄如纸 —— 校验参数 → spawn 一次子进程 → 把 stdout 回成工具结果。这三件事之外一行逻辑都不写。

### 2.3 运行时进程模型

| 进程 | 启动时机 | 生命周期 | 说明 |
|---|---|---|---|
| 桌面壳主进程 | 双击图标 | 常驻 | 窗口、菜单、文件 IO |
| 壳渲染进程 | 随主进程 | 常驻 | 编辑内核 + 界面 |
| dsh 后端 | 首次用 AI 时拉起 | 常驻（可配懒加载） | `--profile sdk`，与壳通过 IPC 通信 |
| Python 引擎 | 每次调用 | **一次性，跑完即退** | 无状态，进程隔离，崩溃不影响壳 |

**为什么引擎做成一次性子进程**：① 无状态，不存在「引擎卡住拖垮整个软件」；② 天然隔离，模板保护闸门在 spawn 前就拦一道；③ 引擎可以单独在命令行跑，测试与排障不需要起整个软件。

### 2.4 技术选型决策（ADR）

| # | 决策 | 选择 | 备选 | 理由 |
|---|---|---|---|---|
| ADR-1 | AI 底座 | **dsh（路线 A+ 装配式）** | 纯自建 / fork / 原样用 | 白送模型适配、工具注册表、沙箱审批、会话留痕；只走 sdk 最小协议面，抽身成本≈0 |
| ADR-2 | 引擎语言 | **Python** | Node/TS | 已用 Python 跑通 171/171 填充；docx 部件级操作生态成熟（lxml + zipfile） |
| ADR-3 | docx 处理方式 | **部件级操作**（zip 读入 → 改 XML → 写回） | python-docx 重排 | 格式 100% 保留；python-docx 重排会丢样式 |
| ADR-4 | 组合包分发 | **tarball（`pnpm pack`）** | npm / github 直装 | 装的是预构建产物，用户无需构建授权；git 直装需 `allowBuilds` 有供应链风险；Windows 上 `link:` 会得到空目录（实测） |
| ADR-5 | 壳技术栈 | **待定：Tauri（原设计）或 Electron** | — | **这是人的问题不是技术问题**，见 §10-C |
| ADR-6 | 编辑内核 | **待定** | genoffice / 开源 docx 编辑器 / 自研 | 判定标准见 §6.2，**决定产品形态能否按原设计走** |
| ADR-7 | 编号主键 | **docId 作唯一主键，docNo 只作展示** | — | 编号在项目内不唯一，不能作索引 |
| ADR-8 | 数据落盘 | **普通文件夹** | 数据库 / 单文件包 | 可拷可传可离线；资料员不装软件也能看 |

## 3. 数据设计

### 3.1 工程文件夹（落盘形态）

```
YY123-岳阳市XX局信息化项目/
├─ project.json                 工程数据：39 字段 + 文档覆盖 + 编号池 + 打印状态 + 目录快照 + 回收站索引
├─ 一、依据分册/
├─ 二、过程分册/
│   └─ 1、开工报审表/                       ← 目录项 = 文件夹
│       ├─ YY123-KGBSB-01_开工报审表.docx    ← 文档 = 文件（编号_表名）
│       ├─ YY123-KGBSB-02_开工报审表.docx
│       └─ 附件/                            ← 附件优先挂目录项
├─ 三、图纸分册/
├─ 四、变更分册/
├─ 五、初步验收与试运行分册/
├─ 六、竣工验收报告/
├─ 七、竣工验收分册/
├─ 八、封面页/
├─ _附件/                        不属于任何目录项的散件
├─ _导出/                        生成的 PDF / 图片
└─ _回收站/                      删除的目录项与文档（可还原）
```

**约定：**
- 目录项文件夹名 = 清单里的序号 + 名称，如 `1、开工报审表`（与 `软件目录.docx` 一致）
- 文档文件名 = `{docNo}_{表名}.docx`，便于脱离软件也能认出来
- `_` 开头的目录是软件自留区，用户不要手工改结构

### 3.2 project.json（工程数据模型）

单一数据文件，`_schema` 作版本标识。**以 `_` 开头的键是软件自留字段，其余是项目级字段值。**

```jsonc
{
  "_schema": "yzproj/1.0",

  // ── ① 项目级字段值（39 个，key 与字段字典一致）
  "projectName": "……", "contractNo": "YY123", "ownerUnit": "……",
  "projectBackground": "……", "buildSite": "……", "weather": "……",
  // …… 其余略

  // ── ② 文档级覆盖：按文档相对路径 → 字段
  "_documents": {
    "二、过程分册/1、开工报审表.docx": { "docNo": "YY123-KGBSB-01" }
  },

  // ── ③ 编号池：按目录项维护
  "_numbering": { /* 见 §3.6 */ },

  // ── ④ 打印状态：按 docId
  "_printStates": {
    "D-KGBSB-01": { "printed": true, "printedAt": "2026-09-12T15:04:00", "times": 2 }
  },

  // ── ⑤ 目录树快照：`软件目录.docx` 解析结果的落盘副本
  "_catalogSnapshot": { "version": "1.0", "parsedAt": "2026-09-12", "items": [ /* 见 §3.3 */ ] },

  // ── ⑥ 文档实例清单：docId → 实例元数据
  "_docs": {
    "D-KGBSB-01": {
      "itemId": "二-01", "relPath": "二、过程分册/1、开工报审表/YY123-KGBSB-01_开工报审表.docx",
      "docNo": "YY123-KGBSB-01", "fillState": "complete", "createdAt": "…"
    }
  },

  // ── ⑦ 回收站索引
  "_trash": [ /* 见 §3.7 */ ]
}
```

**设计要点：**
- **`project.json` 是唯一真源**。树、编号、打印状态全部从这里读，软件启动不用重新扫盘（快）
- **`_catalogSnapshot` 为什么要落盘**：避免每次启动都去解析 `软件目录.docx`（慢且依赖模板资产在场）；同时让工程可脱离原始清单独立打开
- **快照可刷新**：清单升级后，软件可对比「快照 vs 新清单」提示差异，由用户决定是否刷新
- **保持向后兼容**：将来加字段只加 `_` 键；`_schema` 版本号变了走迁移

### 3.3 目录清单模型

`软件目录.docx` 是清单唯一真源。解析后每项形如：

```jsonc
{
  "itemId": "二-01",                       // 稳定 ID：分册序号 + 目录项序号
  "volume": "二、过程分册",                  // 所属分册
  "seq": 1,                                // 分册内序号
  "name": "开工报审表",                     // 目录项名
  "relPath": "二、过程分册/1、开工报审表",   // 工程内的文件夹相对路径
  "hasTemplate": true,                     // 元数据①：模板有无
  "dataType": "工程建设类",                 // 元数据②：资料类型
  "importance": "重要项",                   // 元数据③：重要级别
  "templateFile": "1、开工报审表.docx",     // 有模板时的模板文件名
  "abbr": "KGBSB",                         // 表名缩写（编号用）
```

### 3.4 字段字典模型

```jsonc
{

  "groups": [ { "group": "一、项目基本信息", "fields": [ /* … */ ] } ],
```

### 3.5 文档实例模型与状态机

**两个状态，独立演进：**

```
填写状态 fillState:   empty(未生成) → draft(有缺值) → complete(填全) → error(缺模板/缺必填)
打印状态 printState:   unprinted(未打印) → printed(已打印)
```

**界面上的状态色点（四色）由两个状态合成：**

| 颜色 | 含义 | 判定 |
|---|---|---|
| 灰 | 待填 | 未生成 或 有缺失字段 |
| 绿 | 已填完整 | 必填齐、无残留占位符，未打印 |
| 蓝 | 已打印 | `printState = printed`（优先级高于绿） |
| 红 | 异常 | 缺模板、缺必填项、文件损坏 |

> **注意**：蓝 > 绿 > 灰，红最高。打印过的文档即使后来发现缺字段，也先显示红（异常优先让用户看见）。

### 3.6 编号模型

**编号规则（定稿）：**

```
有合同编号：  {合同编号}-{表名缩写}-{流水号}      例：YY123-KGBSB-01
无合同编号：  {表名缩写}-{流水号}                 例：KGBSB-01
```

| 规则 | 内容 |
|---|---|
| 表名缩写 | 表名每个汉字拼音声母取大写（开工报审表 → `KGBSB`）；括号内说明不参与；软件自动生成、人工可覆盖 |
| 流水号位数 | 默认 **2 位**；施工日志 / 周报 / 月报 / 试运行记录用 **3 位** |
| 续排范围 | **单个目录项内独立续排**，每个目录项各自从 `01` 起 |
| 适用范围 | **只有模板内带「文档编号」标签的 9 项**才编号（见 `表名缩写字典.csv` 的「启用编号」列） |
| 分配时机 | **生成文档那一刻**，取最小可用号，永久绑定 |
| 删除 | 编号释放回**该目录项**号池 |
| 恢复 | 从回收站恢复时**取回原编号**，不重新分配 |
| 重排 | 同目录项内删除后**不重排**（删掉 02，03 仍是 03） |

> **不重排的原因**：已打印的纸质件编号必须与电子件永远一致。实时重排的话，中途删一份会让后号整体前移，发出去的纸质件当场对不上。
> **全项目编号不唯一** —— 每个目录项都从 01 起，`01` 会重复。这是设计前提，索引一律走 `docId`。

**编号池落盘结构：**

```jsonc
"_numbering": {
  "二-01": {                                  // 按 itemId 维护
    "prefix": "YY123-KGBSB",                  // 合同编号 + 表名缩写
    "digits": 2,
    "allocated": [                            // 在册：docId ↔ 号，永久绑定
      { "docId": "D-KGBSB-01", "no": "YY123-KGBSB-01", "at": "2026-09-12" }
    ],
    "released": ["YY123-KGBSB-02"],           // 已释放，可被复用（取最小）
    "max": 2                                  // 历史最大序号，保证「不重排」
  }
}
```

**分配算法（伪码）：**

```
allocate(itemId):
    pool = numbering[itemId]
    if pool.released 非空:
        no = 取 released 中序号最小者; released.remove(no); return no
    pool.max += 1
    return f"{pool.prefix}-{pool.max:0{pool.digits}d}"

release(itemId, docId):
    no = allocated[docId].no; allocated.remove(docId)
    if 序号(no) == pool.max: pool.max -= 1        # 尾部回退，便于复用
    else: pool.released.append(no)                # 中间号留坑，不重排

restore(itemId, docId, no):
    released.remove(no) if no in released
    allocated[docId] = { no }                     # 取回原号
```

### 3.7 回收站模型

```jsonc
"_trash": [
  {
    "trashId": "T-20260912-001",
    "type": "doc",                               // doc（单份）| item（整个目录项）
    "itemId": "二-01",
    "docId": "D-KGBSB-02",                       // type=doc 时有
    "docNo": "YY123-KGBSB-02",
    "originPath": "二、过程分册/1、开工报审表/YY123-KGBSB-02_开工报审表.docx",
    "trashPath": "_回收站/T-20260912-001/…",
    "deletedAt": "2026-09-12T15:10:00"
  }
]
```

**还原规则**：还原时按 `originPath` 回原位；编号走 `restore()` 取回原号；被还原位置若已被占用（同名同号冲突），提示用户改名而非静默覆盖。

### 4.1 引擎总览与统一调用约定

| # | 引擎 | 脚本 | 干什么 | 状态 |
|---|---|---|---|---|
| 1 | 填充 | `fill_engine.py` | 套模板 + 填 39 字段 → 出 37 份 | ✅ v0.1 已跑通 |
| 2 | 残留校验 | `verify_engine.py` | 导出前扫未替换 `{{}}`，拦截放行 | ⏳ 待收编 |
| 3 | 子表识别 | `subtable_engine.py` | 按表头列名识别 8 张表，接管数据行 | ⏳ 待建 |
| 4 | 编号引擎 | `numbering_engine.py` | 按规则分配 / 释放 / 恢复 `docNo` | ⏳ 待建 |
| 5 | 自动汇总 | `aggregate_engine.py` | 施工日志 → 周报 → 月报 | ⏳ 待建 |

**统一调用约定（所有引擎必须遵守）：**

```
python <engine>.py <子命令参数> [--json]
```

| 约定 | 内容 |
|---|---|
| 参数 | 具名长参数（`--project`、`--out`、`--dir` …），不用位置参数 |
| 输出 | `--json` 时 stdout **最后一行**为契约 JSON；不带 `--json` 时输出人类可读文本（供命令行排障） |
| 退出码 | `0` 成功 / `1` 业务失败（校验不通过等）/ `2` 参数错误 / `3` 环境错误（缺依赖、路径不存在、模板缺失） |
| 副作用 | 只写 `--out` 指定的目录；**永不写 `模版/`、`模版_原始备份/`** |
| 幂等 | 同一输入重复跑，结果一致（编号引擎例外，它有意带状态） |
| 无状态 | 引擎自身不存状态，状态全在 `project.json` |

**契约 JSON 统一形态：**

```jsonc
{
  "ok": true,                        // 业务是否成功
  "engine": "fill",                  // 引擎标识
  "summary": "37 份 / 171 处已填充 / 0 处残留",   // 一句话结论（给模型看）
  "stats": { "docs": 37, "filled": 171, "missing": 0, "residual": 0 },
  "items": [ /* 明细，按需 */ ],
  "errors": [ { "file": "…", "part": "…", "key": "…", "reason": "…" } ]
}
```

### 4.2 引擎 1 · 填充引擎

**职责**：读 `project.json` + 字段字典，把模板里的 `{{key}}` 替换为实际值，逐份输出到工程目录。

**核心算法（已验证，不要重写）：**

| 环节 | 做法 | 为什么 |
|---|---|---|
| 取值 | 项目级字段 + `_documents[<docRel>]` 文档级覆盖 | 文档级优先 |
| 定位 | 逐段（`w:p`）拼出全文，再在全文里找 `{{key}}` | **占位符常被 Word 拆到多个 run 里**，逐 run 找必然漏 |
| 替换 | `splice()`：把 `[start, end)` 落在多 run 上的文本替换掉，其余 run 原样保留 | 保住格式；`xml:space="preserve"` 按需增删 |
| 倒序处理 | 同一段内**从后往前**替换 | 避免偏移量失效 |
| 零件处理 | 只处理 `word/document.xml` / `header*.xml` / `footer*.xml` / `footnotes.xml` / `endnotes.xml` | 其它部件不碰，媒体文件逐字节原样 |
| 缺值 | **保留 `{{key}}` 原样**，记入报告 | 宁可导出时报错，不可导出半成品 |
| 日期 | 命中 `date:` 前缀或日期占位符 → 跳过并标注 | 日期一律手写（`datePolicy`） |
| 特殊占位符 | `#rows` / `/rows` / `image:` / `upload:` → 交给引擎 3 或附件通道 | 分工明确 |

**实测成绩**：37 份模板 / 171 处占位符 / **171 命中 / 零残留 / 零部件丢失**。

**v0.1 → v1.0 加固项**：CLI 参数规范化、输出改契约 JSON、退出码对齐、解耦 demo 路径、`main()` 返回值统一。

### 4.3 引擎 2 · 残留校验引擎

**职责**：导出前的最后一道闸门 —— 扫描工程目录，报告未替换的 `{{}}`、未定义 key、日期被误填，并阻断导出。

**判定口径（关键，不许误报）：**

| 情况 | 判定 |
|---|---|
| 文本里有 `{{xxx}}` 且 xxx 是启用字段 key | ❌ **残留**（说明值没填上） |
| 文本里有 `{{xxx}}` 但 xxx 不在字典里 | ❌ **未定义 key**（模板被改坏了） |
| 日期留白（`年　　月　　日`、`日　期：`） | ✅ 正常，不算残留 |
| 正文自然语言里的 `XX`、`×××` | ✅ 正常（但若应为占位符却漏标，走「漏标复查」流程，不由本引擎报） |

**输出**：按 `文件 + 部件 + 位置 + key` 逐个报错；`ok=false`、退出码 `1`。

### 4.4 引擎 3 · 子表识别引擎（技术最难）

**职责**：按 `tablePolicy` 用「表头列名序列」在 docx 里认出 8 张静态表，接管其数据行。

**算法：**

```
1. 遍历文档所有 w:tbl
2. 对每张表，取前若干行拼出「表头列名序列」（去全角空格、忽略空列）
3. 与 tables[].columns 逐项比对：
     完全匹配 → 命中；含信息行 → 跳过前 N 行再比
4. 命中后定位数据区（表头下、表尾上）
5. 按 data 行数调整行数：
     不足 → 克隆末行（连同 w:trPr / w:tcPr / 嵌套属性）
     多余 → 删除末行
6. 逐格写入数据，注意 gridSpan（合并列）/ vMerge（纵向合并）
```

**难点与对策：**

| 难点 | 对策 |
|---|---|
| `w:tblGrid` 列宽定义 | 克隆行时**不动 tblGrid**，只加 `w:tr`；`w:tc` 的 `w:tcW` 沿用原行 |
| 合并单元格 `w:gridSpan` / `w:vMerge` | 按列号映射而非按 `w:tc` 序号映射；纵向合并只在续行写 `w:vMerge`（无 val） |
| 表头识别容错 | 忽略前后全角空格与空列；允许信息行前缀（模板实际存在） |
| 八1 封面只列 5 卷 | 程序按 **8 分册**补齐卷册行 |
| 表样式不崩 | 增删行后跑 `diff_parts.py` 校验：只有目标部件变，样式定义未动 |

**验收**：8 张表逐一跑通；喂 3 行到 6 行空表 → 出 3 行；喂 10 行 → 出 10 行；边框/字体/列宽保持。

### 4.5 引擎 4 · 编号引擎

**职责**：按 §3.6 规则分配 / 释放 / 恢复编号，维护编号池。

**子命令：**

| `--action` | 作用 | 副作用 |
|---|---|---|
| `allocate`（默认） | 为某目录项申请 `count` 个号 | 写 `_numbering`，返回号列表 |
| `release` | 释放某个号（文档被删） | 号入 `released` 或尾部 `max` 回退 |
| `restore` | 恢复某个号（回收站还原） | 从 `released` 移除，绑回 docId |

**必须锁死的测试用例：**
1. 9 个带编号的目录项，各自从 `01` 起，互不干扰
2. 删除 `002` → `003` **仍是** `003`（不重排）
3. 从回收站恢复 `002` → 取回原号
4. 无合同编号 → 降级 `KGBSB-01`
5. 施工日志 / 周报 / 月报 / 试运行记录 → **3 位**流水号

> 「同目录项内不重排」是**已打印纸质件的命根子**，用测试用例锁死，别让人后来"优化"掉。

### 4.6 引擎 5 · 自动汇总引擎

**职责**：按周聚合施工日志 → 周报；按月聚合周报 → 月报。

**输入字段：**

| 源 | 字段 |
|---|---|
| 施工日志 | `weather` / `todayWork` / `workerCount` / `siteIssue` / `coordination` / `buildSite` |
| 周报 | `weeklyDone` / `weeklyUndone` / `weeklyProblem` / `weeklyPlan` |
| 月报 | `monthly*` 四项 |

**聚合规则：**

| 目标字段 | 来源 | 口径 |
|---|---|---|
| `weeklyDone` | 本周各日 `todayWork` | 按日期序拼接，去重合并同类项 |
| 天气统计 | 本周 `weather` | 统计各天气天数（晴 3 天 / 雨 2 天） |
| 人数 | 本周 `workerCount` | **均值 + 峰值**（口径做成配置项，待业务确认） |
| 问题与协调 | `siteIssue` / `coordination` | 非空项汇总 |
| `monthlyDone` | 本月各周报 `weeklyDone` | 二次聚合，沿用同一口径 |

**边界**：跨周 / 跨月的日志不串（按日期归属，不按文档顺序）。

### 4.7 贯穿五引擎：docx 部件级操作规范

| 规则 | 说明 |
|---|---|
| 读 | `zipfile.ZipFile` 读入，逐部件持有 `bytes`，`infolist()` 保序 |
| 改 | 只把目标部件交给 `lxml.etree` 解析 → 改 → 序列化；**其余部件原样写回** |
| 写 | 按原 `infolist()` 顺序 `writestr`，不重排、不重新压缩媒体文件 |
| XML 声明 | 保留原 `<?xml ...?>` 声明 |
| 命名空间 | 用 `{http://schemas.openxmlformats.org/wordprocessingml/2006/main}` 前缀 `w()` |
| 禁止 | 不用 `python-docx` 打开再保存（会重排、丢样式、改媒体） |

**两条硬约定：**
- 组合包**不声明任何 `@deepseek-ai/*` 运行时依赖** —— 全部 external，由宿主 dsh 提供。理由：子包在 npm 依赖图上不完整（`dsh-type-meta` 404），自带反而装不上；且 `resolveBundleDir()` 本就从 dsh 安装目录解析。
- patch 行按**包名**引用（不是相对路径），Node 模块解析才找得到。

### 5.3 五工具映射

| 工具名 | 引擎 | 关键参数 | 说明 |
|---|---|---|---|
| `yanshou_fill` | fill_engine | `outDir?` / `projectFile?` | 一键成册，确定性批处理 |
| `yanshou_verify` | verify_engine | `targetDir?` | 导出前查错 |
| `yanshou_subtable` | subtable_engine | `docPath*` / `tableKey?` / `dataFile?` | 清单表按表头接管行 |
| `yanshou_numbering` | numbering_engine | `catalogItem*` / `count?` / `action?` / `docNo?` | 编号分配/释放/恢复 |
| `yanshou_aggregate` | aggregate_engine | `period*` / `from?` / `to?` / `outDoc?` | 日志→周报→月报 |

**工具 `description` 的写法要求**：能让一个**不认识这个项目的人**选对工具、给对参数；参数校验失败要给**可操作的报错**（不是一句 `invalid arguments`）。

### 5.4 配置层与加载顺序

生效配置在空根之上逐层组合：

```
1. profile.dsh.profile.bundles 所列各组合包 patch，按列表顺序（先是 dsh-base）
2. profile 自己的 cordis.patch.yml
3. $DSH_HOME/cordis.patch.yml
4. 每个 --patch <path> overlay，按 argv 顺序
```

**后层按行胜出，且 patch 替换目标行的整个 `config`，不深合并。** 推论：
- 我们的 patch 按 `id` 覆盖前层时，**必须重述该行需要的每一个键**
- 用户可在自己 profile 里覆盖我们的行，**无需改我们的包** → 默认值要给「用户大概率会保留的」那一套

**安装 / 验证 / 移除：**

```sh
dsh plugin --profile yanshou add ./dsh-yanshou-docs-0.1.0.tgz
dsh --profile yanshou --dump-config      # 应看到 "# == dsh-yanshou-docs" 层
dsh --profile yanshou
dsh plugin --profile yanshou remove dsh-yanshou-docs
```

### 5.5 模板保护（双层机制）

铁律：**AI 绝不写 `模版/` 下的 docx**。

| 层 | 机制 | 状态 |
|---|---|---|
| 第一层（确定性） | `src/policy.ts` 的 `assertWritable()`：所有写盘工具动手前过闸，命中受保护目录抛 `TemplateProtectionError` | ✅ 现已有效 |
| 第二层（全局） | `tools/pre-execute` waterfall 事件拦截，可覆盖到别的插件注册的工具 | ⏳ 待真机确认签名后启用 |

**纪律**：签名**必须先真机确认再写代码**，不许凭猜测（上一轮已在 `link:` 那件事上吃过猜的亏）。签名没确认前保持注释状态，靠第一层兜底。

另：`ctx.sandbox` 是官方记录的「限制所启动的进程」seam，将来可把 Python 子进程纳入沙箱统一管控。

### 5.6 通道与协议

| 项 | 设计 |
|---|---|
| 通道 | `dsh --profile sdk` 的 **JSON-RPC**（127.0.0.1 或 stdio） |
| **不用** | dsh 的 `ui-*` 插件体系 / slot 插槽 —— 会把编辑区绑死在它 UI 骨架上 |
| 理由 | 契约面最小：升级风险被压缩到「agent 协议变了没有」这一件事 |
| 模型 Key | 走环境变量（实测 dsh 用 `apiKeyEnv: DEEPSEEK_API_KEY`），**不写进配置文件** |
| 模型厂商 | 不绑 DeepSeek，dsh 有 `dsh-llm-*` 多厂商适配器 |

### 5.7 留痕

dsh 的会话日志是**追加式、带版本（`session.vN.jsonl`）、有迁移链**，且「模型可见即已记录」是运行时不变量。

→ 意味着「谁、何时、改了哪份哪字段」天然可回放。**验收资料要的正是这个**，将来能拿给甲方看。

### 6.2 编辑内核（决定生死）

**形态定稿**：**流式为主，进入表格单元格切换为网格编辑。**（模板本身是 docx 流式文件，纯 Excel 网格套不上；但表格类资料在网格里编辑效率高得多，所以做局部网格。）

**选定内核必须满足三个条件：**

| # | 条件 | 判定方法 |
|---|---|---|
| 1 | 打开 **37 份模板全部能渲染**，排版不崩 | 逐份打开截图比对 |
| 2 | 编辑保存回去**格式不丢** | 保存后跑 `diff_parts.py`：只有被改的部件变了，媒体文件逐字节一致 |
| 3 | 能拿到打印/页面数据 | 支撑「已打印」标记与 PDF 导出 |

**候选方向**：genoffice（`提示词.docx` 提及）/ 其它开源 docx 编辑器 / 自研（docx 渲染 + contenteditable）。

> ⚠️ **若找不到满足条件的内核，「Office 级所见即所得」需降级为「表单式填写 + 只读预览」—— 属于产品形态变更，必须回来重新拍板。** 所以这件事要最早出结论。

### 6.8 关键流程（一环扣一环）

**① 一键成册**

```
用户点「生成全部」
  → 壳读 _catalogSnapshot + project.json
  → 遍历 56 项：
       有模板(37) → 引擎1 套模板填字段 → 引擎4 分配编号 → 落盘到目录项文件夹
       无模板(18) → 建空白 docx（带项目信息页眉）/ 留上传位 / 标记跳过
  → 引擎3 处理 8 张子表（有数据的）
  → 回写 project.json（_docs / _numbering）
  → 树刷新状态色点
```

**② 单份编辑**

```
左树点某项 → 打开 docx（项目级字段已填好，显示为正常文本）
  → 待填字段浅灰占位 → 用户补完 → Ctrl+S
  → 壳校验必填 → 回写 _documents（文档级覆盖）→ 状态点更新
```

**③ 导出整册**

```
用户点「导出整册 PDF」
  → 引擎2 残留校验（闸门）→ 不通过：列出问题点，中止
  → 通过：逐份 docx → PDF
  → 生成目录页 → 合并 → 统一编页码 → 加页码
  → 输出到 _导出/整册.pdf
```

**④ AI 汇总周报**

```
用户点「生成本周周报」（需联网授权）
  → 壳 → dsh 后端：把本周施工日志字段交给模型
  → 模型调用 yanshou_aggregate（或先归纳再调 yanshou_fill）
  → 引擎按口径取数写文档 → 返回结果
  → 壳展示 + 落盘，会话日志留痕
```

## 7. 接口契约（冻结点）

> **本章是全项目地基。定完冻结；要改走变更记录并通知全队。**

### 7.1 引擎 CLI 契约

| 引擎 | 调用形态 | 必填 | 选填 | 退出码 |
|---|---|---|---|---|
| fill | `--project <json> --templates <dir> --out <dir> [--report <csv>] [--json]` | project / out | templates 默认 `模版/`、report | 0/1/2/3 |
| verify | `--dir <dir> [--dict <json>] [--json]` | dir | dict 默认字段字典 | 0/1/2/3 |
| subtable | `--doc <docx> [--table <key>] [--data <json/csv>] [--json]` | doc | table 留空则自动识别 | 0/1/2/3 |
| numbering | `--item <目录项名> [--action allocate\|release\|restore] [--count N] [--no <docNo>] [--json]` | item | action 默认 allocate | 0/1/2/3 |
| aggregate | `--period week\|month [--from <date>] [--to <date>] [--out <docx>] [--json]` | period | from / to / out | 0/1/2/3 |

### 7.2 统一返回结构

所有引擎 `--json` 时 stdout 最后一行为：

```jsonc
{
  "ok": true,
  "engine": "fill",
  "summary": "37 份 / 171 处已填充 / 0 处残留",
  "stats": { },
  "items": [ ],
  "errors": [ { "file": "", "part": "", "key": "", "reason": "" } ]
}
```

### 7.3 工具参数契约

见 §5.3 表。五个工具的 `parameters` / `output.schema` / `output.render` 必须与引擎 CLI 契约一一对应；工具层只做「参数映射 + spawn + 结果格式化」，不做业务判断。

### 7.4 壳 ↔ 后端协议

| 项 | 设计 |
|---|---|
| 传输 | JSON-RPC over stdio 或 127.0.0.1 |

## 8. 非功能设计

### 8.1 性能

| 指标 | 目标 | 依据 |
|---|---|---|
| 一键成册（37 份） | **≤ 10 秒** | 填充引擎实测约 1 秒，含编号与子表留余量 |
| 单份打开编辑 | ≤ 3 秒 | 取决于编辑内核 |
| 整册导出 PDF | ≤ 60 秒（视页数） | PDF 转换 + 合并 |
| 工程打开 | ≤ 2 秒 | 读 `project.json` + 快照，不扫盘 |

### 8.2 安全

| 面 | 措施 |
|---|---|
| 模板保护 | `assertWritable()` 闸门 + 全局 `pre-execute` 拦截（双层，见 §5.5） |
| 路径穿越 | 引擎只写 `--out` 指定目录；插件层 `shell: false` 防注入 |
| 模型 Key | 走环境变量，不落配置文件 |
| 供应链 | 只用 tarball 分发；**不引入任何需要 `allowBuilds` 授权的包** |
| 数据主权 | 全程本地；AI 功能需联网授权，客户资料不出内网 |
| 留痕 | dsh 会话日志追加式可回放 |

### 8.3 可靠性与可测试性

| 项 | 设计 |
|---|---|
| 引擎单测 | 每个引擎独立可跑（命令行 + `--demo` 即时生成的样本工程），不依赖壳与 dsh |
| 部件级比对 | `diff_parts.py`：逐部件比对，确认「只有该变的变了」 |
| 端到端 | 一条命令走全链路（demo 工程 → 成册 → 校验 → 导出） |
| 幂等校验 | 同输入重跑结果一致 |
| 崩溃隔离 | 引擎一次性子进程，崩溃不影响壳 |

### 8.4 打包与部署

| 项 | 设计 |
|---|---|
| 交付形态 | 安装包 / 免安装包（Windows） |
| 包含 | 桌面壳 + 编辑内核 + dsh 后端 + Python 运行时与依赖 + 模板资产 |
| 硬标准 | **全新 Windows 机器装完直接能用**（用户不需要装 Python / Node / dsh） |
| 风险 | **Python 依赖打包是坑**（lxml 等含原生扩展），需提前验证，别留到最后一天 |

## 9. 设计红线

> 破一条，全盘重来。

| # | 红线 | 为什么 |
|---|---|---|
| 1 | **不动 `模版/` 下任何 docx** | 37 份模板 + 171 占位符是冻结资产，动一次全量复核一次 |
| 2 | **不动 `模版_原始备份/`** | 回滚底牌，删了就没了 |
| 3 | 引擎只读 `模版/`，输出到工程目录，**永不回写原始模板** | 同上 |
| 4 | 缺值**保留 `{{key}}` 原样**，宁可导出报错 | 不可导出半成品给甲方 |
| 5 | docx 一律**部件级操作**，不用 `python-docx` 重排 | 保格式 100% 不丢 |
| 6 | 契约冻结后要改，走**变更记录 + 通知全队** | 契约一动全是返工 |
| 7 | **不 fork dsh、不改 upstream 源码** | 保持「升级=换版本号」「抽身成本≈0」 |
| 8 | 插件安装**只用 tarball**，不用 `link:`、不用 `github:` | 前者 Windows 空目录，后者供应链风险 |
| 9 | **编号在目录项内不重排** | 已打印纸质件的命根子 |
| 10 | 日期**不自动填充**、子表**不在模板侧标注** | 工头已定，属政策不是建议 |
