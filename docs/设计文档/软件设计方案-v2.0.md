## 0. 导读

### 0.1 v1.0 → v2.0 改了什么

v1.0 回答的是「**软件怎么设计**」，骨架已经立住了：分层、数据模型、五块引擎、AI 接入、契约冻结。v2.0 **不推翻任何已定案**，只做四件事：**补空白、给结论、排工序、定复用边界**（最后一项 2026-09-16 追加：先查开源能不能借，再决定要不要自己写）。

| # | v1.0 的状态 | v2.0 的处理 | 对应章节 |
|---|---|---|---|
| 1 | 有「五块引擎」，但**没有"业务规则"这一层** —— 规则散在引擎代码里 | 新增 **规则资产层**：字段字典 + 填数规则 + 表名缩写 + 目录清单，全部外置为可维护资产 | §2.2 / §4.7 |
| 2 | 「自动填数」只在引擎 1 里体现为「取值 → 替换」，**没说清值从哪来、什么时候算** | 全新设计 **来源分级 S0–S6 + 取值决议链 + 触发条件矩阵 T1–T12 + 39 字段策略总表** | **§4（全文）** |
| 3 | **占位符填完即变普通文本** —— 用户手改后软件认不出这是哪个字段，全册同步做不了 | 新增 **字段锚点机制 + 半自动同步策略**（三方案对比后给建议） | §5.3 |
| 4 | ADR-5（壳技术栈）、ADR-6（编辑内核）**悬空**，只说「需真机验证后拍板」 | 给出 **候选实证对比 + 结论建议 + 可执行的验收方法**（用现成 `diff_parts.py`） | §5.2 / §2.5 |
| 5 | 只有「阶段 0–6」粗线条，**没有验收标准** | 重排为 **P0–P7 八个阶段**，每阶段带目标/交付物/**可测验收标准**/依赖/风险 | **§6（全文）** |
| 6 | 功能以「引擎」为组织单位，**没有产品视角的模块划分** | 新增 **14 个功能模块 · 4 组**，每个模块含职责/输入输出/依赖/优先级 | **§3（全文）** |
| 7 | 「对标筑业云」只有一句定位 | 新增 **逐功能对照表**：学什么、不学什么、为什么 | §1.2 |
| 8 | 文档路径写的是旧结构（`.workbuddy/engine/`、`规范/`、`模版/`） | 统一为 **安装资产目录 + 工程数据目录** 双轨制 | §2.6 |
| 9 | **从没做过开源复用调研**，所有组件默认自研 | 新增 **GitHub 实名核查的复用评估**（不凭印象、不信宣传稿）：编辑内核借 genoffice（Apache-2.0）、PDF 借 pypdf、AGPL 组件全部排除。**净省约一个半月到两个月的自研量** | §2.7 · `开源复用评估.md` |
| 10 | 组合包「不声明任何 `@deepseek-ai/*` 依赖」的做法**未经真实插件验证** | 用第三方真实插件 `dsh-univer-office` 的做法校正：**改用 `peerDependencies`**；同时确认 **`dsh.bundle.patch` 机制被真实插件在用** → A+ 路线可行性被实证 | §2.5 ADR-14 · §5.2 |

> **本文与 v1.0 的关系**：v1.0 未被本文修订的内容（数据模型 §3、引擎算法 §4、AI 层 §5、客户端骨架 §6、红线 §9）**继续有效**，本文只做索引不重复。凡本文显式给出的结论（ADR-5/6、锚点机制、触发矩阵），**优先于 v1.0 的对应表述**。

### 0.3 术语增量（v1.0 术语表之外）

| 术语 | 含义 |
|---|---|
| **规则资产** | 字段字典、填数规则、表名缩写字典、目录清单 —— 决定"填什么"的配置，与决定"怎么填"的引擎解耦 |
| **填数规则** | 一条可配置的取值指令：`目标字段 ← 来源 + 变换 + 条件` |
| **FillPlan（填充计划）** | 一次生成/填充前算出的「文档 → 占位符 → 值 → 来源」清单。中间产物，可预览、可审计、可复现 |
| **值来源（Source）** | 一个字段值的来路，分 S0–S6 七级（§4.2） |
| **决议链（Resolution Chain）** | 同一个字段有多个候选值时，按固定优先级裁决出最终值的规则（§4.3） |
| **字段锚点（Anchor）** | 填充后留在 docx 里的隐式标记，让软件永远知道"这段文字来自哪个字段"（§5.3） |
| **作业（Job）** | 一次可长可短的批处理：一键成册、整册导出、清理回收站。有进度、可取消、写日志 |

## 1. 产品定义（增量）

### 1.1 定位一句话（不变）

**建一个工程 = 建一个文件夹；点一次「一键成册」= 套完 37 份模板并填好字段；打完印标记状态；最后整册导出 PDF 归档。39 个项目字段全程只填一次。**

v2.0 给这句话加一个补语：**——但"只填一次"的前提是软件知道值从哪来、什么时候该算、改了要不要回灌。这正是 §4 要解决的事。**

### 1.2 对标筑业云资料：学什么、不学什么

工头要求参考筑业云的**产品形态与功能特点**。先把它的真实功能盘清楚（2026-09-16 核，含官方站与新版 AI 服务公告），再逐条决定取舍。

**它的形态**（对应 `参考图.png`）：顶部菜单条 + Ribbon 图标行（新建/打开/工程导入/保存/附件管理/工程信息 · 打印/预览/展开收起/查找/替换 · 客服/商城/课堂/视频/我的/升级/退出）+ 左侧「表格目录 / 回收站 / 查找结果」三页签树 + 右侧带行列标的表格化编辑区 + 未授权水印。**我们的界面骨架已经照这个定了**（《软件使用方式设计》§3），不需要改。

**它的功能 → 我们的对应取舍：**

| 筑业云功能 | 本质是什么 | 我们的对应设计 | 取舍 |
|---|---|---|---|
| 智能工序 / 工序建表 | 按分部分项自动选表，不落项 | `软件目录.docx` 清单驱动 + 快照建树（M02） | ✅ **学机制**：清单是资产，不硬编码。❌ 不学它的 13 套国标库 |
| 智能台账 | 自动生成"已出/未出资料"清单，查漏补缺 | 目录树**台账视图**：按分册/状态/完成度统计，四色色点 + 完成度环（M02） | ✅ **学，且要加强**（这是它最值钱的功能） |
| 一键形成资料目录 | 生成资料目录清单 | 整册目录页 + 交付用「验收资料目录」（M07/M11） | ✅ 学 |
| 批量导出 PDF | 批量转换合并 | 三档导出（单份/分册/整册）+ 统一页码（M11） | ✅ 学 |
| 自动填表（自动导入工程常用信息） | 工程信息录一次，全表带上 | **39 字段项目档案 + 决议链 + 溯源标记**（M03/M05） | ✅ **学，且做到比它细**：它有"自动带入"，我们有"带入 + 来源可溯 + 冲突可裁决" |
| 自动计算 | 填基础数据，表格自动算 | 子表合计、合同金额 ↔ 设备清单总价校核（M07，二期） | 🔶 二期 |
| 智能评定 / 安全表自动评分 | 检验批检测值评定、加 ○△ 标记 | — | ❌ **不做**：政务信息化项目无检验批概念 |
| 验收数据逐级生成 | 检验批 → 分项 → 分部向上汇总 | **施工日志 → 周报 → 月报** 按日期窗口聚合（M13/引擎 5） | ✅ 学机制，换数据源 |
| 图形编辑器 / 盖章 | 画图嵌入、浮动图片当电子章 | 设备拓扑图插图（M09）；电子章二期 | 🔶 二期 |
| 电子组卷及组卷目录打印 | 分类组卷 + 组卷目录 | 整册导出即组卷（M11） | ✅ 学 |
| AI 秘书 / AI 建表 / AI 填表 / AI 检查 | 问答 + 选表 + 抽取 + 查错 | dsh 驱动：起草润色、智能填表、查错问答（M13） | ✅ **学能力，换底座**：底座走 dsh，**客户资料不出内网**（它走云） |
| 云工程 / 云存储 | 数据上阿里云，多端同步 | — | ❌ **有意不做**：反着来。"文件夹即一套完整资料，可拷可传可离线"是我们的差异点 |
| 多人协同编辑同一份 | 协同 | — | ❌ 不做（共享盘文件锁兜底） |
| 24 万张范例库 | 内容资产 | 不做内容库；自有 37 模板 + 甲方招标文件即范例 | ❌ 不做 |

**结论一句话**：**学它的"台账 + 一键生成 + 自动带入 + 逐级汇总"四样机制，不学它的"国标库 + 云存储 + 评定 + 协同"四样包袱。** 我们的差异化就三条：① 模板驱动、清单可配；② 内建 AI 且数据不出内网；③ 数据落盘为普通文件夹。

### 1.3 功能范围（v1.0 基础上补两块边界）

v1.0 的「明确要做 / 明确不做」两张表继续有效。这里只补两块本次新增的边界 —— **自动填数**和**编辑能力**的边界，详见 §4.10 与 §5.5，摘要：

| 域 | 做什么 | 不做什么 |
|---|---|---|
| 自动填数 | 项目级 21 字段一次录入全册带入；auto 类 3 字段系统计算；8 张子表按表头接管；日志→周报→月报聚合；编号自动分配 | **不自动填日期（12 项全停用）**；不自动填签字/意见/专家栏；不自动填固定文案；不用 LLM 做确定性批处理 |
| 文档编辑 | E0 只读预览 → E1 表单式填写 → E2 正文流式编辑 → E3 表格结构化编辑 → E4 插图/页眉页脚（分级见 §5.1） | 不做公式/图表/批注/修订/邮件合并域；不做多节精细页面设置；不做排版级"像 Word 一样"的兜底承诺 |

### 1.4 领域概念模型（增量部分）

v1.0 的四级结构（工程 → 分册 → 目录项 → 文档）不变。本次在其上补三样东西：

```
工程（文件夹）
├─ 分册 × 8 → 目录项 × 55 → 文档实例 × N          （v1.0 已定）
│
├─ 项目档案（39 字段）                              （v1.0 已定：字段字典 v2.3）
│   └─ 每个字段值带 **来源标记**：S0–S6            ← 新增
│
├─ 规则资产（只读，随安装包）                       ← 新增
│   ├─ 字段字典.json      「有哪些字段、什么类型、必不必填」
│   ├─ 填数规则.yaml      「每个字段的值从哪来、怎么算」   ← 本次新增的关键资产
│   ├─ 表名缩写字典.csv   「编号用什么缩写、几位流水」
│   └─ 软件目录.docx      「有哪些分册、哪些目录项、有没有模板」
│
├─ FillPlan（每次生成前的取值计划）                ← 新增
│   └─ 文档 → 占位符 → 值 → 来源 → 规则ID → 时间
│
└─ 字段锚点（嵌在 docx 里）                        ← 新增
    └─ 段落/单元格内 `yz_<key>` 锚点 + 值快照 → 支撑"改了要不要回灌"
```

**为什么把「规则资产」和「FillPlan」单独拎出来**：工头问的核心是"依据业务规则自动填数"。如果规则写在引擎代码里，那每次改口径（比如人数从"均值"改"峰值"）都要改代码、重打包、重测。**规则外置成资产后，改口径 = 改一行 YAML。** FillPlan 则是让这件事"看得见"的手段 —— 生成前先给工头看一张表：这份文档的这个格子，填什么值、从哪来、按哪条规则。看得见才敢信。

## 2. 整体架构

### 2.1 架构总图（v2.0）

v1.0 是四层（壳 / dsh / 引擎 / 数据）。v2.0 补一个**规则资产面**和一条**留痕审计线**，形成"四层 + 两个横切面"：

```
┌════════════════════════════════════════════════════════════════════╗
║  L1 · 形态层  桌面壳（自建，命根子）                                 ║
║  Ribbon · 三页签树/台账 · 编辑区 · 打印预览 · 导出 · 回收站 · 作业面板 ║
║  编辑内核：docx 保真渲染 + 表单填写 + 正文/表格编辑（§5.2 选型）      ║
╚═══════════════════════════════╤════════════════════════════════════╝
                                │ 本地 IPC（127.0.0.1 JSON-RPC / stdio）
┌───────────────────────────────▼────────────────────────────────────┐
│  L2 · 智能层  dsh（upstream 一行未改）                              │
│  dsh --profile yanshou（sdk 契约面）                                │
│  ├─ @deepseek-ai/dsh-base   模型适配·工具注册表·沙箱审批·会话留痕    │
│  └─ dsh-yanshou-docs（组合包，树外，tarball 分发）                   │
│       tools: _fill / _verify / _subtable / _numbering / _aggregate   │
│              + _datafill（新增）· _docgen（新增）                    │
│       policy: 模板保护（拒绝写 templates/**）                        │
└───────────────────────────────┬────────────────────────────────────┘
                                │ spawn（argv 传参，shell: false）
┌───────────────────────────────▼────────────────────────────────────┐
│  L3 · 引擎层（Python，确定性，真正干活）                             │
│  ①datafill 取值装配  ②fill 模板填充  ③docgen 文档生成/追加           │
│  ④subtable 子表接管  ⑤numbering 编号  ⑥aggregate 汇总  ⑦verify 校验  │
│  全部：无状态 · 一次性子进程 · 契约 JSON · 退出码 0/1/2/3            │
└───────────────────────────────┬────────────────────────────────────┘
                                ▼
┌────────────────────────────────────────────────────────────────────┐
│  L4 · 数据层（普通文件夹，不依赖任何框架）                           │
│  工程目录：project.json + 8 分册 docx + 附件 + 回收站 + 导出         │
└────────────────────────────────────────────────────────────────────┘

╔══ 横切面 A · 规则资产（只读，随安装包分发，可升级） ══════════════════╗
║ 字段字典.json │ 填数规则.yaml │ 表名缩写字典.csv │ 软件目录.docx      ║
║ 模板资产 templates/（37 份，受保护）                                 ║
╚═══════════════════════════════════════════════════════════════════════╝
╔══ 横切面 B · 留痕与审计 ═════════════════════════════════════════════╗
║ dsh 会话日志（追加式 JSONL，模型可见即已记录）                        ║
║ + 壳侧操作日志（作业/字段变更/打印/删除还原，写工程内 _logs/）        ║
╚═══════════════════════════════════════════════════════════════════════╝
```

**与 v1.0 的三处实质变化：**

1. **引擎从 5 块变 7 块** —— 新增 `datafill`（取值装配，把"业务规则"从 fill 里剥出来）与 `docgen`（文档生成/追加，把"造文件"从 fill 里剥出来）。理由：v1.0 的 fill 一个引擎干两件事（取值 + 替换 + 生成），改一处就要全量重测；拆开后 **fill 变成纯函数**（输入：文档 + 值表；输出：文档），可以单独跑单测。
2. **规则资产独立成面** —— 不再埋在代码里。
3. **留痕从"AI 层顺带"变成"两层都有"** —— dsh 只记 AI 会话；工程内的字段变更、打印、删除还原必须壳侧记，因为**离线时也得有痕迹**。

### 2.2 分层职责与边界（v2.0 版）

| 层 | 只做 | 绝不做 | 为什么这么切 |
|---|---|---|---|
| **L1 形态层** | 界面、交互、编辑、打印、导出、文件夹读写、作业调度 | 不做任何文档内容计算 | 编辑内核与 AI 完全解耦，换 AI 底座不动壳 |
| **L2 智能层** | 模型调度、工具注册、审批、会话留痕 | 不做文档处理、不碰 UI | 只走最小协议面，把 dsh 变更风险挡在编辑内核之外 |
| **L3 引擎层** | 确定性数据变换（取值/生成/填充/识别/编号/汇总/校验） | 不联网、不调模型、不写模板 | 输入固定输出唯一 → 100% 可复现，可单测 |
| **L4 数据层** | 存 | — | 普通文件，整包拷走即完整资料 |
| **横切 A 规则资产** | 定义"填什么、怎么算" | 不含任何处理逻辑 | 改口径不改代码 |
| **横切 B 留痕** | 记 | 不做业务判断 | 验收资料要的正是可追溯 |

**一句话记牢**：**L3 是"会干活的"，L2 只是"会喊话的"，横切 A 是"规矩"，横切 B 是"账本"。**

### 2.3 运行时进程模型

| 进程 | 启动时机 | 生命周期 | 说明 |
|---|---|---|---|
| 桌面壳主进程 | 双击图标 | 常驻 | 窗口、菜单、文件 IO、作业调度 |
| 壳渲染进程 | 随主进程 | 常驻 | 编辑内核 + 界面 |
| dsh 后端 | 首次用 AI 时拉起（可配懒加载 / 常驻） | 常驻 | `--profile yanshou`，IPC 通信 |
| Python 引擎 | 每次调用 | **一次性，跑完即退** | 无状态，进程隔离，崩溃不影响壳 |

**v2.0 补充：作业（Job）模型。** 一键成册、整册导出这类动作可能跑十几秒到一分钟，不能阻塞 UI：

```
壳建立作业 → 分配 jobId → spawn 引擎 → 流式读 stdout（进度行）→ 写 _logs/jobs.jsonl
                                      ↘ 用户可取消（kill 子进程）
                                      ↘ 完成后统一刷新树状态 + toast 结果
```

引擎进度输出协议：stdout 每行 `#PROGRESS <done>/<total> <描述>`，契约 JSON 仍是**最后一行**（与 v1.0 一致，不破坏契约）。

### 2.5 技术选型决策（ADR · v2.0 收口版）

v1.0 的 ADR-1~4、7、8 不变。本次把两个悬空的拍掉，并新增 5 条：

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| ADR-5 | **壳技术栈** | ✅ **Electron**（2026-09-16 定） | genoffice 的 `docx-engine` 是纯 TS 独立包且官方壳就是 Electron，复用其 shell/打包/更新经验最省；Tauri 更轻但省下的体积换不回"少踩一遍坑"。**这是人的问题不是技术问题**，工头一个人干 → 选生态最厚的 |
| ADR-6 | **编辑内核** | ✅ **genoffice `@genoffice/docx-engine` 为主选**（待 1 天保真验证，见 §5.2 验证清单） | 实测依赖仅 4 个（`pptx-engine` / `fast-xml-parser` / `jszip` / `utif2`），**无 electron、无原生模块、无 AI 依赖**，可干净嵌入；「字节保留往返」与红线 5 同源；Apache-2.0 |
| **ADR-9** | **填充后是否留锚点** | ✅ **留**（bookmark + customXml 双写） | 不留锚点 = 全册同步、来源追溯、字段级校验全部做不了 |
| **ADR-10** | **规则存放位置** | ✅ **外置 YAML 资产** | 改口径不改代码 |
| **ADR-11** | **规则引擎与填充引擎是否合并** | ✅ **拆开** | fill 变纯函数，可单测；规则可预览 |
| **ADR-12** | **项目级字段被手改后的策略** | ✅ **半自动**：检测 → 提示 → 用户选（同步全册 / 仅本份 / 忽略） | 全自动会把用户在某一册的合理特例改掉；全手动等于没同步 |
| **ADR-13** | **AI 能否直接写文档** | ✅ **不能** | AI 只能产出候选值或调用工具；落盘一律走引擎闸门 |
| **ADR-14** | **组合包如何声明 dsh 依赖** | ✅ **用 `peerDependencies` 声明**（不是完全不声明） | 实测第三方插件 `dsh-univer-office` 就是这么做的；宿主版本不匹配时**加载期响亮报错**，优于运行时莫名失败。**修订 v1.0 的"完全不声明"做法** |
| **ADR-15** | **PDF 工具链** | ✅ **`pypdf`**（合并/加页码），**排除 PyMuPDF** | pypdf ★10,204；PyMuPDF 虽 ★10,717 但 **AGPL-3.0**，商用需授权 |
| **ADR-16** | **是否引入 AGPL 组件** | ✅ **一律不引入** | ONLYOFFICE / SuperDoc / ranuts / PyMuPDF 全是 AGPL-3.0。自用无碍，但"将来给同行用"这个可能性必须留住 |
| **ADR-17** | **是否直接用 `dsh-univer-office`** | ⏸ **不直接依赖**，仅作参考与过渡 | 它绑 dsh 的 web UI 体系（`client.inject: dsh-client-ui-*`），用了就等于接受 dsh 界面形态，违背"编辑区自建"的核心风险控制；且它是通用 Office 能力，非业务能力 |

### 2.6 目录结构规范（v2.0 新增，解决 v1.0 路径混乱）

v1.0 里 `.workbuddy/engine/`、`规范/`、`模版/` 三个路径混着用。v2.0 定死**双轨制**：

**(A) 安装资产目录**（随软件安装，只读，升级覆盖）

```
<安装目录>/assets/
├─ templates/                  37 份模板（受保护，红线）
│   一、依据分册/ … 八、封面页/
├─ spec/                       规则资产（§2.1 横切 A）
│   ├─ 字段字典.json
│   ├─ 填数规则.yaml           ← 本次新增
│   ├─ 表名缩写字典.csv
│   └─ 软件目录.docx
├─ engine/                     Python 引擎（7 个脚本）
└─ runtime/                    内嵌 Python 运行时（免装 Python）
```

**(B) 工程数据目录**（用户创建，可拷可传，永不被安装包覆盖）

```
YY123-岳阳市XX局信息化项目/
├─ project.json                工程数据（字段 + 覆盖 + 编号池 + 打印状态 + 快照 + 文档清单）
├─ 一、依据分册/ … 八、封面页/  按目录项建文件夹，文档落在里面
├─ _附件/                      不属于任何目录项的散件
├─ _导出/                      生成的 PDF / 图片
├─ _回收站/                    删除的目录项与文档
└─ _logs/                      操作日志（作业、字段变更、打印、删除还原）
```

**跨目录引用规则（开发必须遵守）：**
- 引擎读模板一律从 `assets/templates/`，**输出一律到工程目录**，永不回写模板
- `assets/` 只读；任何写操作命中 `assets/templates/**` 直接抛 `TemplateProtectionError`
- 工程目录内 `_` 开头为软件自留区，用户不要手工改结构

### 3.3 模块详述

#### M01 · 工程底座

| 项 | 内容 |
|---|---|
| **职责** | 新建 / 打开 / 最近打开 / 从文件夹导入 / 工程属性；`project.json` 的读写、`_schema` 迁移、原子写入（临时文件 + rename，防断电写坏） |
| **边界** | 不解析清单（M02 干）、不碰字段语义（M03 干）。**它是唯一的工程文件 IO 出口** —— 别的模块不许直接写 `project.json` |
| **关键实现** | 单文件真源 + 内存缓存 + 脏标记；写盘走 `project.json.tmp` → rename；每次写入前自动留一份 `_logs/backup/project-YYYYMMDD-HHmm.json`（保留最近 20 份） |
| **验收** | 断电拔 U 盘模拟测试：不产生 0 字节 `project.json`；20 个工程来回切换无错 |

#### M02 · 清单与目录树

| 项 | 内容 |
|---|---|
| **职责** | 解析 `软件目录.docx` → 结构化快照；建四级树；三页签（表格目录 / 回收站 / 查找结果）；节点状态色点；**台账视图**（完成度统计） |
| **边界** | 清单是**资产**，软件不提供界面编辑分册/目录项结构（要改走 M04 的资产维护流程） |
| **关键实现** | ① 快照落盘（v1.0 已定），启动不扫盘；② **完成度算法**：分母 = 必须项（有模板项 + 重要上传项），分子 = 已填完整的文档；③ 台账三种口径切换：按分册 / 按状态 / 按重要级别 |
| **对标筑业云** | 「智能台账 + 查漏补缺」正是它的招牌。我们的台账要能做到：**一眼看出"还差哪几项、差在哪"**，点一下直接跳到那份文档 |
| **验收** | 56 项全部建树；人为删除某目录项后台账分母正确变化；色点四态（灰/绿/蓝/红）判定与 v1.0 §3.5 一致 |

#### M03 · 项目档案

| 项 | 内容 |
|---|---|
| **职责** | 按字段字典渲染分组表单（7 组 39 字段）；必填强制校验（`projectName`/`ownerUnit`/`constructionUnit` 三项 + `contractNo` 条件必填）；**每个输入框旁显示值的来源标记**；保存后触发派生值重算与影响提示 |
| **边界** | 不渲染 12 个停用的日期字段（`datePolicy.enabled=false`）；不渲染 23 个归档字段 |
| **关键实现** | ① 建档引导只要 4 项核心（v1.0 已定），其余可后补；② **变更影响提示**：改了 `projectName` → 弹「影响 37 份文档，是否全册回灌？」（策略见 §4.9）；③ 字段来源角标：手工=实心、继承=灰、推导=蓝、系统=绿、空=红点 |
| **验收** | 三项必填缺失时无法保存；改一处项目级字段后提示出现且选择"仅本份"不会污染其他文档 |

#### M04 · 规则资产

| 项 | 内容 |
|---|---|
| **职责** | 加载四份资产；**对账**（字典字段 ↔ 模板实际使用 key 必须严格相等）；体检（占位符扫描、未定义 key、孤儿字段、缩写字典缺项、模板缺失） |
| **边界** | **只读资产、不改模板**。发现问题只出报告 + 给修复建议，修复动作由工头手动完成（v1.0 分工约定） |
| **关键实现** | 把 `03_工具脚本/` 里 12 个脚本收编为正式能力：`scan_placeholders` / `verify_placeholders` / `field_usage_diff` / `gen_abbr_dict` / `gen_field_mapping` / `diff_parts` 等；对外只暴露一个「资产体检」按钮 + 一份报告 |
| **验收** | 体检报告 0 误报（日期留白、自然语言 `XX` 不算问题）；人为改坏字典后能准确报出未定义 key |

> 这是 v1.0 里最容易被忽略但最要命的一块 —— 上一轮已经吃过「字典与模板不一致 → 静默漏替」的亏（规范 §六 坑 9）。**每次改资产必须过体检。**

#### M05 · 填数引擎（本次新增，核心）

| 项 | 内容 |
|---|---|
| **职责** | 按 §4 的规则体系，为**每一份文档**算出**每一个占位符**的最终值，产出 FillPlan |
| **边界** | **不写盘**（只算不写，写盘是 M06 的事）；不调模型；不做格式处理 |
| **输入** | `project.json` + `字段字典.json` + `填数规则.yaml` + 快照 + 文档上下文（docId / docNo / 目录项 / 日期） |
| **输出** | `FillPlan`（docId → {key: {value, source, ruleId, resolvedAt}}）+ 缺值清单 + 冲突清单 |

| **验收** | 39 字段逐一给值或明确标记为空；同输入两次运行 FillPlan 完全一致（幂等）；改一条规则只影响该规则的目标字段 |

### 3.4 MVP 边界（第一个"能干活"的版本）

**MVP = M01 + M02 + M03 + M04 + M05 + M06 + M08 + M09(E0/E1) + M10 + M11 + M14(回收站部分)**

用一句话说清 MVP 的能力：**建档 → 清单一键成册（37 份套模板填好）→ 表单式补填缺项 → 校验 → 打印标记 → 整册导出 PDF。**

不在 MVP 里的：M07 子表（子表先用空白表格，人工填）、M12 附件、M13 AI、M09 的 E2/E3 编辑。

**为什么把子表踢出 MVP**：子表是最难的一块（合并单元格 / 行克隆），但它**不阻塞主线**。没有子表，工头照样能出整册 PDF，只是清单类表格要手填。先让主线跑通，再啃硬的。

## 4. 自动填数：数据来源与触发条件

> 这是 v2.0 的核心章。目标：**让"软件自动填了哪些数、为什么这么填、什么时候填"变成看得见、改得动、追得到的事。**

### 4.1 先澄清一个问题：为什么"自动填数"不等于"查找替换"

v1.0 的填充引擎已经能做到 171 处占位符 100% 命中。但那只是**执行**。真正难的是**决策**：

| 问题 | v1.0 的答案 | v2.0 的答案 |
|---|---|---|
| 这个字段的值从哪来？ | 从 `project.json` 取 | **分级：S0–S6，每级有明确边界**（§4.2） |
| 同一个字段有好几个候选值怎么办？ | 文档级覆盖项目级（两层） | **七层决议链 + 来源标记**（§4.3） |
| 什么时候算这个值？ | 生成文档那一刻 | **12 个触发点，各管一段**（§4.4） |
| 用户改了正文里的值，要不要回灌档案？ | 没有机制 | **锚点 + 半自动同步**（§4.9 / §5.3） |
| 改一条口径（比如人数取峰值）要改什么？ | 改代码 | **改一行 YAML**（§4.6/4.7） |
| 生成出来为什么是这个值？ | 只有 CSV 报告 | **FillPlan 可预览、可审计**（§4.8） |

**一句话**：v1.0 解决了"填得进去"，v2.0 要解决"填得对、说得清、改得动"。

### 4.2 数据来源分级（S0–S6）

每一个字段的最终值，都必然来自下面七级之一。**级越高越"自动"，越靠后越"人工"，也越不容易被覆盖。**

| 级 | 名称 | 谁提供 | 典型字段 | 可被谁覆盖 | 界面表现 |
|---|---|---|---|---|---|
| **S0** | 系统生成 | 引擎按规则算出，用户**不可编辑** | `docNo`（文档编号）、序号、卷册行号、目录页页码 | 仅编号可由人工"手动指定"（需显式操作） | 绿色角标 · 只读输入框 |
| **S1** | 项目档案（手工） | 工头在建档/填报时录入 | 21 个项目级字段（`projectName`、三方单位、人员、地点…） | 文档级覆盖 | 实心角标 · 正常可编辑 |
| **S2** | 项目级推导 | 引擎从档案字段算出 | 参建单位的格式化值（万元 2 位、电话规范化）、`buildSite` 拼接 | 文档级覆盖 | 蓝色角标 · 可编辑（改了就升级为 S1） |
| **S3** | 文档级覆盖 | 用户在某一份文档里改的值 | `handoverPlace`（只在移交表里不同）、某份日志的 `weather` | **不被自动覆盖** | 实心角标 + "本份专用"标签 |
| **S4** | 跨文档推导 | 引擎从**其他文档**的数据算出来 | `weeklyDone` ← 本周施工日志 `todayWork`；`trialRunUserCount` ← 试运行记录行数；`monthly*` ← 周报 | 生成后转为 S3（可人工修） | 蓝色角标 + "来自 N 篇日志" |
| **S5** | 上传/识别 | 从上传件（中标通知书、合同）中抽取 | `contractNo`、`constructionUnit`、`contractAmount` | 确认后转 S1 | 橙色角标 · 必须人工确认 |
| **S6** | 人工留白 | **永远不由软件填** | 12 个日期字段、签字/盖章/意见栏、专家手写内容、固定文案 | — | 浅灰提示 · 不参与校验 |

**三条硬规矩：**
1. **S6 的清单是封闭的**，写死在规则文件里，任何人（包括 AI）不得把它们改成自动填。（v1.0 政策，本次固化为代码可校验的约束）
2. **S5 的输出永远是候选值**，必须人工确认才落库。绝不静默写入。
3. **S0 的值一旦分配到 `docId` 就永久绑定**（v1.0 §3.6 编号规则），不因重算而变化。

### 4.3 取值决议链（同一个字段，多个候选值怎么裁决）

v1.0 只有两层（文档级覆盖 > 项目级）。本次扩为**七层**，**从下往上依次覆盖，上面的赢**：

```
                       ┌─ 被覆盖的顺序（越靠上优先级越高）─┐
  ① 文档级·人工锁定   doc_manual       用户在某份里明确改过、且选了"仅本份"     ← 最高，永不被自动覆盖
  ② 文档级·跨文档推导 doc_derived      weeklyDone 这类，用户已在生成后手调过
  ③ 文档级·覆盖       doc_override     project.json 的 _documents[路径][key]
  ④ 项目级·人工       project_manual   档案里工头录的值
  ⑤ 项目级·推导       project_derived  引擎从档案算出的值（格式化/拼接）
  ⑥ 系统生成          system           编号、序号、页码（仅 S0 字段）
  ⑦ 空                empty            以上都无 → **保留 {{key}} 原样**，记缺值
```

**裁决出来的每个值都带 `provenance`（出处）**，结构见 §4.8。界面上的表现：

| 显示 | 含义 | 用户能做什么 |
|---|---|---|
| 正文黑色 | 人工录的值 | 直接改 |
| 正文带蓝色虚线底 | 引擎推出来的值 | 改 → 提示"这是自动算的，确定要覆盖吗？" |
| 浅灰占位 | 还没值 | 点一下就地填 |
| 全文变红 | 必填但没有值 | 保存时拦 |
| 悬停显示小气泡 | `来源：本周 5 篇施工日志（规则 agg.weeklyDone）` | **这就是"说得清"** |

**冲突提示（必须做）**：同一字段在①和④都有值时，软件不静默选一个，而是标黄并在填数面板列出「本份值 / 档案值」，让用户点选。

### 4.4 触发条件矩阵（T1–T12）

工头问的"触发条件"，本质是：**什么时机、因为什么事件、对多大范围、算什么、写不写盘。**

| # | 触发点 | 触发条件（前置） | 动作 | 范围 | 写盘？ | 失败处理 |
|---|---|---|---|---|---|---|
| **T1** | 建档完成 | 用户点"创建工程"且三项必填齐 | 解析清单 → 建快照 → 建树 → 重算项目级派生值（S2） | 全工程 | 写 `project.json` | 清单解析失败 → 阻断建档，报"清单资产异常" |
| **T2** | **一键成册**（手动） | 用户点"生成全部"（v1.0 决策 3：手动触发，不自动跑） | 逐项生成/更新文档 → 算 FillPlan → 填充 → 绑编号 → 处理子表 | 全部 56 项 | 写工程目录 + `_docs`/`_numbering` | 单项失败不中断整批，收集错误后统一报告 |
| **T3** | 单份生成 | 右键目录项 →「生成一份」 | 仅生成该目录项的一份新文档 | 单份 | 同上 | 模板缺失 → 走三选一出路 |
| **T4** | 打开文档 | 左树点击文档 | **运行时求值**：已填值渲染为正文、空值渲染为浅灰占位、标出来源 | 单份 | **不写盘**（纯渲染） | 文件损坏 → 提示 + 标红 |
| **T5** | 保存文档 | `Ctrl+S` | 收集文档级覆盖（含用户改过的锚点值）→ 回写 `_documents` → 判断是否需要全册回灌提示 | 单份 + 提示 | 写文档 + `project.json` | 文件被 Word 占用 → 提示"请先关闭 Word" |
| **T6** | 新增日志类文档 | 用户点"新建今日施工日志" | 从模板生成、编号 3 位、按日期排序 | 单份 | 同上 | — |
| **T7** | **周报/月报聚合** | 用户点"生成周报"；**前置：该日期窗口内存在施工日志** | 按日期窗口取日志 → 聚合（S4）→ 生成正文候选 → 写入周报 | 单份 | 同上 | 窗口内无日志 → 明确报"本周无日志，无法汇总"，不生成空周报 |
| **T8** | 清单/资产变更 | 资产文件版本号变化 | 刷新快照 → 对比新旧清单 → **只提示差异**，由用户决定是否应用 | 全工程 | 提示为主 | 新增目录项需人工确认后才建 |
| **T9** | **导出前闸门** | 用户点导出 | 跑 M08 四类校验 | 全工程 | **不改数据** | `ok=false` → 阻断导出并列问题点 |
| **T10** | 打印完成 | 系统打印回调返回成功 | 写已打印状态 | 单份 | 写 `_printStates` | 打印取消 → 不标记 |
| **T11** | AI 触发 | 用户显式要求（起草/抽取/汇总） | LLM 产候选值 → **人工确认** → 落为 S1/S3 | 字段级 | 确认后才写 | 未联网 → 入口置灰，功能不可用但不影响其他 |
| **T12** | 打开工程时的巡检 | 每次打开工程 | 一致性巡检（编号断号、值冲突、文件缺失）→ **只报告不改** | 全工程 | 不写盘 | 报告进状态栏角标 |

**四个必须讲清的触发纪律：**

1. **T2 绝不自动触发。** 一键成册是重操作（覆盖风险），永远手动（v1.0 决策 3）。
2. **T4 只渲染不写盘。** 打开文档不产生任何副作用 —— 否则每次点开都在改文件，留痕会被污染。
3. **T7 有前置**：没有日志就没有周报。宁可报错，不生成空表。
4. **T9/T12 只读**。校验与巡检永远不改数据 —— 改了就没法判定"是不是人干的"。

### 4.5 39 字段填数策略总表

**每一个字段的来源级、触发点、可否覆盖、空值后果 —— 全部定死。这张表就是 `填数规则.yaml` 的人读版。**

**分组一 · 项目基本信息（7）**

| 字段 | 中文 | 来源 | 触发 | 可覆盖 | 空值策略 |
|---|---|---|---|---|---|

### 4.6 派生规则库

自动填数里"推"出来的值（S2/S4），全部由**规则**描述。规则分 9 类：

| 类型 | 语义 | 示例 | 用在哪 |
|---|---|---|---|
| `direct` 直接映射 | 值 = 档案字段 | `ownerUnit ← project.ownerUnit` | 大部分项目级字段 |
| `alias` 别名归一 | 从自然语言/上传件里认字段 | "承包人" → `constructionUnit` | 智能填表（T11） |
| `format` 格式化 | 变换格式 | `contractAmount` 保留 2 位小数；`constructionPhone` 去空格 | S2 |
| `compose` 拼接 | 多字段拼 | `buildSite ← ownerUnit + [楼栋]` | S2 |
| `aggregate` 汇总 | 多篇文档文本合并去重 | `weeklyDone ← 本周日志 todayWork` | S4（T7） |
| `statistic` 统计 | 计数/均值/峰值 | 天气天数统计、人数均值+峰值 | S4 |
| `count` 计数 | 计数派生 | `trialRunBusinessCount ← 试运行记录行数` | S4 |
| `reference` 引用 | 引用系统生成值 | `docNo ← numbering.allocate(itemId)` | S0（T2/T3） |
| `condition` 条件 | 有/无则不同 | 无监理 → 监理栏留白；无合同号 → 编号降级 | 全局 |

**口径可配置项（本期必须暴露给用户，因为业务口径会变）：**

| 口径 | 选项 | 默认 | 状态 |
|---|---|---|---|
| 周报人数 | 均值 / 峰值 / 均值+峰值并列 | 均值+峰值 | ⏳ **待工头拍板** |
| 施工日志去重 | 完全相同文本合并 / 全保留 | 合并 | 建议：合并 |
| 天气统计格式 | "晴 3 天 / 雨 2 天" / "晴、晴、雨…" | 统计式 | 建议：统计式 |
| 试运行人数口径 | 去重计数 / 人工填 | — | ⏳ **待拍板** |
| 试运行业务笔数口径 | 行数合计 / 人工填 | — | ⏳ **待拍板** |

### 4.7 填数规则文件规范（`assets/spec/填数规则.yaml` 草案）

**这是本次新增的核心资产文件。** 结构草案（不是最终版，供评审）：

```yaml
version: 1.0
# ── 全局策略（与字段字典保持一致，字典是唯一真源，这里只做引用声明）
policies:
  dateAutoFill: false            # 日期一律不自动填（S6）
  subtableMode: program-side     # 子表程序端识别
  manualFields:                  # S6 封闭清单：永不自动填
    - signDate, docDate, startDate, endDate, creationDate, logDate,
      reviewTime, handoverTime, initialAcceptanceDate, acceptanceDate,
      trialRunStartDate, dataGovernanceDate
    - expertScoreList, expertOpinion, expertLeader, expertMembers

# ── 规则（每条：目标字段 ← 来源 + 变换 + 条件）
rules:
  - id: proj.ownerUnit
    target: ownerUnit
    type: direct
    from: project.ownerUnit
    source: S1
    on: [T1]

  - id: fmt.contractAmount
    target: contractAmount
    type: format
    from: project.contractAmount
    transform: { num: true, decimals: 2 }
    source: S2
    on: [T1]

  - id: agg.weeklyDone
    target: weeklyDone
    type: aggregate
    from: docs(itemId="二-10").dateWithin(window.week).field(todayWork)
    transform: { dedup: true, order: date, join: "；" }
    source: S4
    on: [T7]
    require: { minDocs: 1 }        # 前置：窗口内至少 1 篇日志
    fail: block                    # 不满足则报错，不生成空周报

  - id: agg.monthlyDone
    target: monthlyDone
    type: aggregate
    from: docs(itemId="二-11").dateWithin(window.month).field(weeklyDone)
    source: S4
    on: [T7]

  - id: cnt.trialRunBusiness
    target: trialRunBusinessCount
    type: count
    from: docs(itemId="五-06").field(trialRunList).rows
    source: S4
    on: [T7]

  - id: ref.docNo
    target: docNo
    type: reference
    from: numbering.allocate(itemId)
    source: S0
    on: [T2, T3]
    bind: permanent                # 一次分配永久绑定

  - id: cond.noContract
    when: { empty: project.contractNo }
    then: { docNo.prefix: "{abbr}" }     # 无合同编号 → 降级
    else: { docNo.prefix: "{contractNo}-{abbr}" }

# ── 子表数据源
tables:
  deviceList:   { source: S1, path: "project._assets.devices" }
  documentList: { source: S4, from: "catalog.docs" }        # 从工程实际文档生成
  volumeList:   { source: S0, from: "catalog.volumes" }      # 按 8 分册补齐
```

**规则引擎的三条纪律：**
1. **规则只能引用字典里存在的字段** —— 引用不存在的 key，加载期直接报错（响亮失败，参照 dsh 的 Schemastery 哲学）
2. **一条规则只干一件事** —— 不写"既格式化又汇总"的复合规则，否则无法定位问题
3. **规则变更要留痕** —— 规则文件带 `version`，工程里记"本工程按规则 v1.0 生成"，换版本后旧工程能复现

### 4.9 用户改了正文里的值怎么办（半自动同步）

这是 v1.0 最大的空白。场景：工头打开了 37 份里的某一册，把"承建单位"从"湖南省俊昇伟业信息科技有限公司"手改成简称。软件怎么办？

**三步策略（ADR-12）：**

```
① 检测（保存时）
   壳遍历文档锚点 → 拿锚点值 vs 档案值 → 不一致就是"被改过"
        ↓
② 提示（不静默处理）
   ┌──────────────────────────────────────────────┐
   │ 本份文档的「承建单位」已改为：                │
   │   湖南省俊昇伟业信息科技（简称）              │
   │   档案值：湖南省俊昇伟业信息科技有限公司      │
   │                                              │
   │  [ 只改本份 ]  [ 同步到项目档案（影响 36 份）] [ 撤销 ] │
   └──────────────────────────────────────────────┘
        ↓
③ 落库
   · 只改本份   → 写 _documents[路径][key]（S3，本份专用）
   · 同步档案   → 改项目级值（S1）→ 下次生成时其他文档跟进（不自动回写已有文档，只提示）
   · 撤销       → 恢复锚点值
```

**为什么不自动回灌**：工头在某一册里写简称，很可能就是"这一册要简称"，全自动会把 36 份全改掉。**半自动 = 少点两下鼠标，但绝不出错。**

**锚点的技术实现**见 §5.3。

### 4.10 绝不自动填的清单（S6 封闭集）

**日期（12 项）**：`startDate` `endDate` `creationDate` `docDate` `signDate` `logDate` `reviewTime` `handoverTime` `initialAcceptanceDate` `acceptanceDate` `trialRunStartDate` `dataGovernanceDate`
→ 工头 2026-09-12 定：**所有日期一律人工手写**。软件不渲染表单、不注入占位符、不参与残留校验。编辑区可给日期选择器辅助手打（属编辑辅助，不属自动填充）。

**签字/意见/专家栏**：`expertScoreList`（评分表）、专家组组长/成员、各类意见栏、接收人签名、盖章位
→ 这类内容是**现场手写/手签**，软件填了反而不合规。

**固定文案**：如施工日志"质量安全检查"三段、六 8 质保期承诺书正文
→ 模板里已写死，不走字段。

**约束固化**：以上清单写进 `填数规则.yaml` 的 `policies.manualFields`，引擎加载时校验 —— **若有人（或 AI）试图给这些字段自动填值，直接报错拒绝**。

### 4.11 缺值与失败处理（与 v1.0 一致，此处集中声明）

| 情形 | 处理 |
|---|---|
| 字段无值 | **保留 `{{key}}` 原样**（v1.0 红线 4），记入 FillPlan 的 `missing` |
| 必填无值 | 允许生成，但文档标红；**导出时被 M08 阻断** |
| 规则执行失败 | 单项失败不中断整批；记入 `errors`，该字段按"无值"处理 |
| 模板缺失 | 走三选一出路（空白 / 上传位 / 跳过） |
| 编号池冲突 | 编号引擎拒绝分配并报错，不猜测 |
| 前置条件不满足（如无日志生周报） | **拒绝生成**，明确报原因（不生成空文档） |

## 5. 文档编辑：能力范围与内核选型

### 5.1 能力分级（E0–E5）

**先把"编辑"这件事拆成 6 级，逐级定死做与不做。** 分级的意义：**每一级都能独立交付，且上一级是下一级的降级方案** —— 万一编辑内核不达标，产品形态不会崩，只是停在前一级。

| 级 | 名称 | 能力 | 用户能干什么 | 交付阶段 |
|---|---|---|---|---|
| **E0** | 只读预览 | docx 保真渲染、分页视图、缩放、搜索 | 看 | **MVP** |
| **E1** | **表单式填写** | 按字段字典渲染右侧表单 → 值写入占位符；占位符浅灰高亮、点击就地填 | 把该填的字段填完，不碰排版 | **MVP** |

- E2/E3 的价值在于"不用跳出软件去 Word 里改"。**但请保持诚实：如果编辑内核只能到 E1，产品的正确表述是「资料自动生成 + 表单式补填」，而不是「Office 级编辑器」。**

### 5.3 编辑与填数的边界：字段锚点机制（ADR-9）

**问题**：v1.0 的 `{{key}}` 填完就是普通文本。用户改了、软件认不出、全册同步做不了、来源追溯断链。

**方案**：填充时**同时写两样东西**：

```
① 正文里写值（看得见的）
   岳阳市财政局业务系统信息化建设项目

② 正文里埋锚点（看不见的，但可定位）
   <w:bookmarkStart w:id="9001" w:name="yz_projectName"/>
   岳阳市财政局业务系统信息化建设项目
   <w:bookmarkEnd w:id="9001"/>

③ 部件里存台账（不污染正文，存来源与快照）
   word/customXml/item1.xml  ← { "yz_projectName": { value, source, ruleId, at } }
```

| 实现方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **a. 书签 bookmark 包裹** | Word 原生支持、兼容性最好、影响最小、可定位可替换 | 书签过多时 Word 里略乱（可默认隐藏） | ✅ **采用** |
| b. 内容控件 SDT + tag | 结构化最强、可锁定不可编辑 | 在 Word 里显示为灰色控件框，影响观感；会被用户误删 | 🔶 局部用（签字栏等需要锁定的位置） |
| c. customXml 部件 | 不污染正文、数据与文档分离 | 单靠它无法定位"这段文字"，只能靠文本匹配 | ✅ **采用（作为 ② 的配套台账）** |

**最终方案 = a + c**：书签负责**定位**，customXml 负责**记住来源与快照**。

**锚点带来的四个能力：**
1. **全册同步**：改名 → 扫所有文档找 `yz_projectName` 锚点 → 精准替换（不靠文本匹配，绝不会误伤正文里同名的字）
2. **来源追溯**：鼠标悬停格子 → 显示"来自项目档案，2026-09-16 录入"
3. **变更检测**：保存时比对锚点值 vs 档案值 → 触发半自动同步提示（§4.9）
4. **导出校验**：扫锚点比扫 `{{}}` 更准 —— 能区分"字段没填"和"正文里本来就有花括号"

**风险与对策：**

| 风险 | 对策 |
|---|---|
| 用户在 Word 里手工删了书签 | 保存时检测锚点缺失 → 该字段降级为"普通文本"，不再参与同步（不报错，只提示） |
| 书签 id 冲突 | 统一分配段 `9000+`，生成时查重 |
| 与模板既有书签冲突 | 只认 `yz_` 前缀，其他一律不动 |

### 5.5 明确不做（编辑能力边界）

| 不做 | 原因 |
|---|---|
| 公式（`=SUM()`）、图表、SmartArt | 我们的模板里没有；做了维护成本极高 |
| 批注 / 修订模式（track changes） | 单人作业无协同需求；改错靠锚点还原即可 |
| 邮件合并域 `MERGEFIELD` | 规范 §七 已否决 |
| 多节页面设置（不同节不同纸张/横竖混排） | 模板已定死页面设置，不需要软件改 |
| 绘图画布 / 形状工具 | 拓扑图走"插入图片"通道（M12），不在软件里画图 |
| 宏 / VBA / 插件脚本 | 安全红线 |
| 「和 Word 一模一样」的保底承诺 | **不做这个承诺**。目标是"模板保真 + 日常改动够用"，不是替代 Word |

> **诚实声明**：本软件的正确表述是「**验收资料的自动生成与管理系统，内建够用的文档编辑能力**」，不是「Office 替代品」。这句话建议直接写进软件关于页。

### 5.6 编辑与打印/导出的关系

```
打开文档(E0/E1) → 编辑(E2/E3) → 保存(写锚点+覆盖)
                                     ↓
                            打印预览 → 打印 → 标记已打印
                                     ↓
                            导出前闸门(M08) → 导出 PDF/图片/docx
```

**关键约束**：**编辑、打印、导出三者共用同一份渲染结果**。若编辑内核与导出所用渲染器不是同一个（比如编辑用 genoffice、导出用 LibreOffice），会出现"屏幕上好好的、PDF 里错位"的经典事故。**对策：导出优先复用编辑内核的渲染输出（打印为 PDF），只有在需要合并整册时才换 PDF 工具链，且必须有"所见即所得"抽样比对。**

- **P2 结束时就能在命令行出完整整册** —— 万一界面迟迟不达标，工头靠命令行 + Word 也能干活

## 7. 契约增量（v1.0 §7 的补充，原契约不变）

> v1.0 §7 已冻结的 5 个引擎 CLI 契约、统一返回结构、壳↔后端协议**继续有效**。本章只补本次新增的两块引擎与两份资产格式。

### 7.1 新增引擎 CLI 契约

| 引擎 | 调用形态 | 必填 | 选填 | 退出码 |
|---|---|---|---|---|
| **datafill** | `--project <json> --out <fillplan.json> [--dict <json>] [--rules <yaml>] [--only <itemId>] [--json]` | project / out | dict（默认资产字典）、rules、only | 0/1/2/3 |
| **docgen** | `--project <json> --item <itemId\|all> [--count N] [--mode template\|blank\|upload\|skip] [--templates <dir>] [--out <dir>] [--json]` | project / item | count 默认 1、mode、templates、out | 0/1/2/3 |
| **fill**（扩展） | 原参数 + `[--plan <fillplan.json>]` `[--anchor on\|off]` | 同 v1.0 | plan 默认运行时算；anchor 默认 on | 0/1/2/3 |

**进度输出（新增，不破坏契约）**：stdout 允许输出 `#PROGRESS <done>/<total> <描述>` 行，工具层忽略这些行，契约 JSON 仍是**最后一行**。

### 7.2 FillPlan schema

见 §4.8。要点：`values[].source` 必须是 `S0`–`S6`；`conflicts` 必须给出 `resolved` 与理由；`missing` 与 `manualPending` 分开（前者是真缺，后者是本就不该自动填的）。

### 7.3 填数规则 schema

见 §4.7。要点：每条规则**必须有 `id`、`target`、`type`、`source`、`on`**；`type` 只允许 §4.6 的 9 类；`from` 引用的字段必须在字典中存在，否则**加载期报错**。

### 7.4 三个版本号必须对齐

| 版本 | 位置 | 变化时怎么办 |
|---|---|---|
| `_schema`（工程数据） | `project.json` | 走迁移脚本，旧工程可打开 |
| `ruleSetVersion`（规则资产） | `填数规则.yaml` | 工程里记"按 vX 生成"；换版本后旧工程可复现 |
| `version`（字段字典） | `字段字典.json` | 新增字段向后兼容；删字段进 `removedFields` 归档 |

**硬规矩：一个工程必须能说清自己是按哪三个版本生成的**（写进 `project.json` 的 `_generatedWith`）。
