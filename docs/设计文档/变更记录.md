| **改前备份** | `01_设计文档/_历史版本/模板字段映射表-2026-09-16-改前(191条).csv` |

### 为什么改

映射表是**扫原始模板**生成的标注工作记录（见 `模板占位符标准化规范.md` §二），但**占位符注入完成后从未回填对齐**。实测（body 级逐段/逐单元格审）发现三类偏差：

1. **位置漂移**：原表记的段号/单元格与注入后不符（注入过程合并了空段、表格行号变化）。
   - 例：七-6 竣工验收申请函，原表 7 个字段记在「段6」，实况在「段5」。
2. **覆盖缺口**：模板里已注入 `{{key}}` 的位置，原表**完全没有行**。共 **15 个位置**。
   - 例：二-10 施工日志的 `todayWork / workerCount / siteIssue / coordination` 四个字段（**导致"施工日志驱动自动生成"无映射依据**）。
   - 例：二-4 施工组织方案的 `projectBackground / projectGoal / projectContent`。
3. **写法不可解析**：`目标字段` 列混用自然语言，程序无法直接消费。
   - `（含 a/b/c）` ×12 行、`constructionContact/constructionPhone` ×1 行、**`（含 ?）` ×1 行（内容未定）**。

### 改了什么

| # | 动作 | 数量 |
|---|---|---|
| 1 | **目标字段列归一化**为 `字段A\|字段B` 竖线分隔，`@` 标记原样保留 | 全表 |
| 2 | **位置按实况校正**（四轮分配算法：精确命中 → key 锚定 → @ 类型签名锚定 → 兜底） | 17 行 |
| 3 | **补录**实况有 `{{key}}` 而原表无覆盖的位置 | +15 行 |
| 4 | 新增 **`来源`** 列，标注每行的核定方式 | 全表 |
| 5 | **`（含 ?）` 定点结论**：七-3 数据治理承诺书 段7 是**日期留白**（"计划于××年××月××日前完成"），无自动填字段 → 判为 `@manualDate` | 1 行 |

### 6.1 引擎当前**完全跑不起来**（P0 级）


| 代码路径 | 实际解析 | 存在 |
|---|---|---|
| `BASE / '规范' / '字段字典.json'` | `E:\项目资料\规范\...` | ❌ → **启动即崩** |

受影响：二-4（4 处）/ 二-10（5 处）/ 二-8（1 处）/ 六-6（2 处）/ 六-9（1 处）/ 七-1（1 处）。

### 7.2 🔴 本轮翻车记录：T1/T7 是假阳性，已撤回

**我一度报出「6 份模板段前分页失控 → 每段强制新起一页 → 会打成 15–21 页废纸」，工头已批准动手，删除工具也已写好。复核时发现结论是错的。**

**错在哪**：`w:pageBreakBefore` 是 OOXML **on/off 类元素**，必须读 `w:val`：

```xml
<w:pageBreakBefore/>            → 启用
<w:pageBreakBefore w:val="1"/>  → 启用
<w:pageBreakBefore w:val="0"/>  → ★ 关闭！★
```

本包 199 处的实际形态**全是 `<w:pageBreakBefore w:val="0"/>`** —— 是「**显式关闭**」，Word 另存/复制时固化格式的正常产物。

`audit_typography.py` 初版**没读 `w:val`，把"存在"当成了"启用"**。

**复核实测**：全包 37 份 → **真启用 0 处 / 显式关闭 199 处**；真启用段前分页的模板 **0 份**。

**差点造成的后果**：`fix_typography.py` 会删掉 199 处 `w:val="0"` —— 无害但**毫无必要，且是对冻结模板的无谓改动**。安全网在**预演阶段**就拦住（真启用 0 处 → 拒绝动手）。

**处置**：
1. `audit_typography.py` 增加 `is_on(el)` 判定，只认真启用；脚本头注释写死这条纪律
2. `fix_typography.py` 重写为 val-aware（按 `w:val` 筛选 + span 倒序删除），目标 0 时拒绝动手；头注释完整记录这次翻车
3. **一个 docx 都没改** —— 实测 37 份源 ↔ 备份仍逐字节一致，无 `.tmp` 残留

**这是本项目第四次同类假阳性**（前三次：正则剥标签造"数字垃圾"、段落拼串造"漏检 11 处"、`mc:Fallback` 双读造"第 4 页第 4 页"）。
**共性：都是"看元素/文本存在，就下结论"，而没读它的语义属性。**

段24 的 `w:pPr` 里带自动编号：

```xml
<w:numPr><w:ilvl w:val="0"/><w:numId w:val="1"/></w:numPr>
```

对应 `word/numbering.xml` 的 `numId=1 → abstractNumId=0`，lvl0 定义：

```xml
<w:start w:val="4"/>              <!-- 起始就是 4 -->
<w:numFmt w:val="chineseCounting"/> <!-- 中文数字（一二三…） -->
<w:lvlText w:val="%1、"/>          <!-- 渲染成「四、」 -->
<w:suff w:val="nothing"/>          <!-- 编号后不加分隔 -->
```

→ **Word 里它本来就显示成「四、变更分册」**。只是自动编号不进 `w:t`，所以我按纯文本提取才看不见。

**如果我按原建议去改，会变成「四、四、变更分册」。** **已撤回，段24 一个字未动。**

> **8 个分册标题的编号方式对照**：仅段24 用自动编号，其余 7 个（一/二/三/五/六/七/八）是手写文本。功能上等价，**都正确**。
> **这是本项目第 9 次假阳性**，模式 = **「只看 `w:t`，没看段落级属性（`numPr` / `numbering.xml`）」**。与教训 #7（on/off 要读 `w:val`）同族：**文本提取看不到"渲染层"的东西。**
